1. INTRODUCTION                                           *paseo-introduction*

paseo.nvim hands the confusing parts of your own diff to an agent without
leaving Neovim -- including the question of WHICH agent wrote a hunk and what
it was asked to do.

The review workflow itself -- the changed-files picker, the hunk quickfix
list, staging -- is deliberately NOT here. It is ordinary Neovim plumbing with
no Paseo in it, so it belongs in your config, built on the git data layer this
plugin does own. See |paseo-git|.

It is built around a `workspace`: one named unit of work spanning N git
worktrees, plus the untracked context they need. A worktree is per-repo; a
workspace is not, which is what lets a single unit of work span several repos
under a parent directory that is not itself a git repository.

Agents run on Paseo <https://github.com/getpaseo/paseo>, which abstracts
claude / codex / opencode.

==============================================================================
2. REQUIREMENTS                                           *paseo-requirements*

Hard:
  - Neovim 0.11+
  - `git`
  - a Nerd Font -- every surface draws glyphs from one; see |paseo-glyphs|
  - telescope.nvim, for the workspace and agent-session pickers
  - gitsigns.nvim, for finding the hunk under the cursor (|:Paseo-ask|)
  - nvzone/volt, for the chat chrome, the panels and the permission dialog

Optional, for the agent half:
  - the `paseo` daemon, running
  - `bun`, or node >= 22, for the sidecar

Optional, for pasting images into the composer:
  - `wl-paste` (Wayland), `xclip` (X11) or `pngpaste` (macOS)

Run `:checkhealth paseo` to see what is present. Missing optional pieces cost
you the surfaces that need them; the review half is local git and works with
nothing running.

==============================================================================
3. SETUP                                                         *paseo-setup*

>lua
    require("paseo").setup {}
<
`setup()` is required. It merges configuration, registers |:Paseo|, and
installs a DirChanged hook that drops the resolved-repo cache.

==============================================================================
4. CONFIGURATION                                         *paseo-configuration*

Defaults: >lua
    require("paseo").setup {
      paseo = {
        -- url and home are absent by default: absent means "discover it".
      },

      ui = {
        surface = "float",        -- or "sidebar", or "buffer"

        style = "plate",          -- frame language
        colors = "auto",          -- or "fixed": ignore the colourscheme
        palette = {},             -- the eight base colours, by name
        theme = {},               -- highlight group overrides

        float = {
          width = 94,             -- percent of the editor, 1-100
          height = 86,
          -- row and col are absent: absent means centred
          composer = 7,           -- MOST rows the composer may grow to
          composer_min = 3,       -- ...and the fewest it rests at
          zindex = 30,            -- below the 50 a float gets by default
          backdrop = true,
          tab_keys = true,
        },

        buffer = {
          open = "here",          -- the window you are in; "tab" for its own
          chrome = false,         -- hide tabline/statusline while it is up
          composer = function(lines)
            return math.max(7, math.floor(lines / 3))
          end,
          -- composer_min, zindex and tab_keys are inherited from `float`
        },

        sidebar = {
          width = 40,             -- percent of the editor's columns
          min_width = 60,         -- ...but never narrower, in cells
          composer = 8,           -- rows the composer gets
          composer_min = 3,       -- ...and the fewest
          position = "right",     -- or "left"
        },

        terminal = {
          keys = { next = "<C-j>", prev = "<C-k>",
                   sessions = "<C-s>", terminal = "<C-l>" },
          presets = {},           -- extra entries for `c`
        },
      },

      workspaces = {
        dir = ".workspaces",
        branch_prefix = "ws/",
        open = "tab",             -- <CR> in the picker: a new tab, `tcd`'d in
      },

      review = {
        agents = true,
      },

      quit = {
        warn_active_agents = true,
      },
    }
<
                                                      *paseo-config.paseo.url*
paseo.url                                                 string, unset

    Daemon WebSocket endpoint, e.g. `"ws://127.0.0.1:6767/ws"`. Leave it unset
    and the endpoint is discovered; setting it pins the endpoint and skips
    discovery. See |paseo-daemon-discovery|.

                                                     *paseo-config.paseo.home*
paseo.home                                                string, unset

    Overrides `$PASEO_HOME`, which itself defaults to `~/.paseo`. Only affects
    where `config.json` is read from during discovery.

                                                 *paseo-config.paseo.provider*
paseo.provider                                            string, unset

    `provider/model` for agents this plugin creates, e.g.
    `"claude/claude-sonnet-5"`. Unset means "ask the daemon what is ready",
    which is the only answer that survives moving to another host.

                                                *paseo-config.paseo.autostart*
paseo.autostart                                       boolean, default true

    Start the daemon when nothing answers. The alternative is every agent
    action failing until you go and start it by hand -- which is precisely the
    trip out of Neovim this plugin exists to remove.

    It only ever runs `paseo daemon start` when NOTHING answered: against a
    running daemon that command exits 1 and prints a wall of daemon logs, so
    "start it just in case" is not an option. It also refuses to run the
    desktop binary; see |paseo-no-cli|.

                                                   *paseo-config.ui.surface*
ui.surface                                        string, default `"float"`

    Which surface |:Paseo-chat| opens on. Three of them:

      `"float"`    the full-screen dashboard, floating over your code. The
                 default, because it is the surface with everything on it.
      `"sidebar"`  the narrow pane beside your code, for a conversation you
                 glance at rather than the thing you are doing.
      `"buffer"`   the SAME dashboard as `"float"` -- same chrome, same six
                 tabs, same panes -- in a real window with a buffer of its
                 own, taking over the window you are standing in and using
                 the whole screen rather than 94% of it.

    `<C-f>` switches between the float and the sidebar at any time, and a chat
    REMEMBERS the surface you last put it on. `<C-f>` does NOT reach the
    buffer surface and nothing about that is an oversight -- see
    |paseo-chat-buffer|. Use |:Paseo-buf|.

    See |paseo-chat-float|, |paseo-chat-buffer| and |paseo-chat-sidebar|.

                                                    *paseo-config.ui.expand*
ui.expand                                       string, default `"running"`

    How much of a tool card is open before you touch it.

    `"running"` expands a command WHILE it runs and folds it when it succeeds,
    so you watch the output arrive; a failure stays open, because a failure is
    the one you wanted to read. `"always"` and `"never"` are the two ends.
    `<Tab>` overrides whichever it is. See |paseo-chat-timeline|.

                                                      *paseo-config.ui.style*
ui.style                                 string|table, default `"plate"`

    The frame language: how a card is drawn, and what the outer edge of a
    float is. A preset name, or a table of the same fields when you only want
    to change one of them. >lua
        ui = { style = "rounded" }
        ui = { style = { preset = "rounded", border = "none" } }
<
    `card` is one of:

    `"plate"`    NO frame at all. A title row and a body painted one
                 elevation step above the surface, with a row of padding
                 above and below. The default.
    `"rule"`     A title, then one hairline INSET from both edges -- a
                 full-bleed rule reads as a table border, not a divider.
    `"rounded"`  Real boxes, `╭╮╰╯`, with the title inset in the top rule.
    `"square"`   The same with `┌┐└┘`.

    `border` is one of `"invisible"` (the default), `"rounded"`, `"single"`
    or `"none"`.

    `"invisible"` is NOT `"none"`. It keeps a real border and paints the
    glyphs fg == bg, so the frame becomes a one-cell ring of padding in the
    surface's own colour. Dropping the border instead takes that padding with
    it and puts content hard against the window edge.

    A DRAWN edge is painted with `PaseoSurfaceBorder`, which carries the
    surface's own background. It used to be `PaseoBorder`, which has none, so
    the glyphs rendered on the EDITOR's background and the framed styles lost
    the one cell of padding the unframed ones get -- which is what made the
    frame read as a hairline pasted onto the editor rather than as the edge of
    a raised sheet.

    There is no rule under the tab bar in ANY style. It survived for the
    framed ones and was the "three frame weights in one window" complaint in
    miniature: the float's own edge, a full-bleed rule directly under the
    pills, and a box around every card below it. The pills are a row of filled
    shapes and delimit the bar by themselves. The ROW stays -- dropping it
    would shift every section below, and volt does not recompute those.

    Every style produces the SAME number of rows for the same content. That is
    not tidiness: volt records a section's start row when the layout is
    measured and never recomputes it, so a card whose height depended on the
    frame would move every section below it the moment this changed.

    See |paseo-colours|.

                                                     *paseo-config.ui.colors*
ui.colors                                        string, default `"auto"`

    Where the eight base colours come from.

    `"auto"`     Derive them from the colourscheme. This is what makes the
                 dashboard look like it belongs to whatever you have loaded,
                 and it is re-derived on every |ColorScheme|.
    `"fixed"`    Use the plugin's own instead, and do not follow the
                 colourscheme at all. For a theme whose colours the agent
                 surfaces read badly in, or which simply is not what you want
                 them to look like. >lua
        ui = { colors = "fixed" }
<
    See |paseo-colours|.

                                                    *paseo-config.ui.palette*
ui.palette                                            table, default `{}`

    The eight base colours, by name, laid over WHICHEVER source
    |paseo-config.ui.colors| names. Each is a `#rrggbb` string; anything
    absent comes from that source. >lua
        ui = { palette = { blue = "#7aa2f7" } }
        ui = { colors = "fixed", palette = { bg = "#1a1b26" } }
<
    `red`      Failure, and a destructive permission.
    `green`    Success, and the agent's own voice.
    `blue`     Your voice, headings, paths, and the seed the eight identity
               swatches are rotated off.
    `yellow`   Running, and a warning.
    `grey`     Everything that has to recede: dividers, labels, disabled rows.
    `border`   Frames, where a style draws them.
    `text`     Body text.
    `bg`       The background the five elevation tiers are stepped off, and
               what every accent ramp blends towards. Leave it UNSET on a
               transparent theme: absent is what tells the derivation there is
               nothing to build tiers on, and painting an opaque rectangle
               over someone's wallpaper is worse than having no card.

    This is a TOKEN, not a highlight group, and that is the difference between
    it and |paseo-config.ui.theme|. Everything below still runs on what you set
    here -- the elevation ladder, the four accent ramps, the contrast
    corrections -- so naming two colours still gets a coherent set, and the
    colour reaches every group derived from it rather than the one group you
    happened to name.

                                                      *paseo-config.ui.theme*
ui.theme                                              table, default `{}`

    Highlight overrides, laid over the derived groups AFTER derivation and
    re-applied on every |ColorScheme|. The LAST word. >lua
        ui = { theme = { PaseoChipOn = { bg = "#204a26" } } }
<
    A config key rather than "set the group again after setup()", which is
    what the docs used to say and which quietly stopped working the moment you
    changed colourscheme -- the derivation re-runs and overwrote it. The same
    is true of |paseo-config.ui.colors| and |paseo-config.ui.palette|: all
    three are read on every re-derivation.

    See |paseo-colours| for the group names.

                                                    *paseo-config.ui.animate*
ui.animate                                 boolean|table, default on

    Motion. `false` disables every effect; a table names them: >lua
        ui = { animate = { bars = true, flash = true, fps = 30 } }
<
    `bars`    Ease a progress bar towards its new value rather than snapping.
              The context-window bar is the one that benefits: a jump from
              40% to 70% reads as a glitch.
    `flash`   Briefly tint a tool card as it settles to ok or failed, then
              fade out through the accent ramp.
    `fps`     Frames a second, clamped to 1-60.

    The spinner is NOT one of these and is never disabled: a turn that is
    running has to look different from one that is wedged, and that is
    information rather than decoration.

    Neither effect changes a section's HEIGHT, which is a constraint rather
    than a choice: volt records each section's start row when the layout is
    measured, so a section that grows mid-animation draws every section below
    it at the wrong row.

    A third effect -- staggering a panel's rows in on a tab switch -- was
    written and then removed. A list's rows are all addressable the moment it
    is drawn, so a reveal that painted only some of them left the screen
    disagreeing with what a keypress would do for the length of it.

                        *paseo-config.ui.float*
                        *paseo-config.ui.float.width*
                        *paseo-config.ui.float.height*
ui.float.width                                        number, default `94`
ui.float.height                                       number, default `86`

    The full-screen surface's box, as a PERCENTAGE of the editor, 1-100.

    That is the unit nvzone/floaterm's `size` takes, computed with the same
    arithmetic in the same order -- so a number means the same thing in either
    config, and the two windows agree to the cell rather than to within a
    rounding error. floaterm's `size = { h = 90, w = 92 }` is: >lua
        ui = { float = { width = 92, height = 90 } }
<
    Percentages rather than a margin in cells because a margin that looks
    right on a 200-column monitor is most of a laptop screen. 1-100 rather
    than fractions because `0.92` and `92` are each obvious once you know
    which convention you are in, and nothing on the page tells you which.

    Either may instead be a FUNCTION -- the escape hatch for a size no
    percentage can express. It is handed `vim.o.columns` or `vim.o.lines` and
    returns CELLS.

    Clamped to 60x20, below which the tab bar and the composer stop fitting,
    and to the editor, so no setting can put the border off screen.

                        *paseo-config.ui.float.row*
                        *paseo-config.ui.float.col*
ui.float.row                                          number, unset
ui.float.col                                          number, unset

    Where the box sits, in absolute editor CELLS -- these are window
    coordinates, not sizes, and "row 3" is what you mean when you pin a
    window.

    Unset means centred, with the same `(total - size) / 2` floaterm centres
    with. So giving the two the same size puts them in the same place, and
    switching between them does not move the frame under you.

                                              *paseo-config.ui.float.composer*
ui.float.composer                    number or function, default `7`

    The MOST rows the composer may take. It rests at
    |paseo-config.ui.float.composer_min| and grows with what you type, up to
    this; the conversation takes back whatever it is not using. See
    |paseo-chat-composer|.

    A box standing at its full height over an empty buffer was the largest and
    emptiest shape on the screen, which is why this is a ceiling and not a
    fixed size.

    A FUNCTION is handed the surface's rows and returns cells. That is what
    |paseo-config.ui.buffer| `composer` defaults to: a ceiling written in cells
    fits one terminal, and the buffer surface is the whole screen.

                                          *paseo-config.ui.float.composer_min*
ui.float.composer_min                                 number, default `3`

    And the FEWEST -- the height the box rests at over an empty buffer.

    This was 1, which is the same mistake as a flat seven in the other
    direction: one row is the shape of `:e `, not of the place you write a
    paragraph, and it is what every session opens on. Set `1` for the old
    behaviour.

                                                *paseo-config.ui.float.zindex*
ui.float.zindex                                       number, default `30`

    Base z-index of the full-screen surface. Below 50 on purpose -- see
    |paseo-chat-zindex|. The dimmed backdrop sits five below this and the
    conversation and composer five above; the permission dialog ignores it
    entirely and stays on top of everything.

                                              *paseo-config.ui.float.backdrop*
ui.float.backdrop                                 boolean, default true

    Dim the editor behind the full-screen surface.

                                              *paseo-config.ui.float.tab_keys*
ui.float.tab_keys                                 boolean, default true

    Bind bare `1`-`6` to the dashboard's tabs in the conversation and the
    composer as well as in the chrome. They have to be bound there or they do
    nothing, because the Chat tab puts your cursor in the composer.

    The cost is that a bare digit is also a COUNT: while the dashboard is open,
    `3p` and `5j` in those two buffers go to the tab bar. Set this false to
    keep the counts -- `<M-1>`-`<M-6>` and `<Tab>` still switch tabs, and
    collide with nothing.

                                                 *paseo-config.ui.sidebar*
ui.sidebar                                                          table

    The sidebar, in the same units as the float. >lua
        sidebar = {
          width = 40,        -- percent of the editor's columns, or a function
          min_width = 60,    -- ...but never narrower than this, in CELLS
          composer = 8,      -- the MOST rows the composer grows to
          composer_min = 3,  -- ...and the fewest
          position = "right" -- or "left"
        }
<
    `min_width` exists because a percentage cannot know when it has produced a
    pane too narrow to read a tool card in: 40% of a 100-column terminal is 40
    columns. The float's equivalent floor is fixed at 60x20 instead, because
    there it is a hard layout requirement rather than a matter of taste.

    `composer` and `composer_min` read exactly as the float's do, and the
    sidebar's box grows the same way: three rows over an empty buffer, up to
    the ceiling as you type, and back again when you send. A fixed eight rows
    here was a third of a narrow pane spent on whitespace for the whole of a
    session.

    The width is also capped at what 'winwidth' leaves for the window you came
    back from. Neovim claws the difference back the instant focus returns
    there, so a bigger number is not a wider sidebar -- it is a number that
    quietly does not happen.

                                                  *paseo-config.ui.buffer*
ui.buffer                                                           table

    The dashboard as a WINDOW rather than as a float -- |paseo-chat-buffer|. >lua
        buffer = {
          open = "here",     -- or "tab", for a tab page of its own
          chrome = false,    -- keep the editor's tabline and statusline?
          composer = function(lines)
            return math.max(7, math.floor(lines / 3))
          end,
        }
<
    There is no `width` or `height` here, and that is the point of the
    surface: the host window's size IS the geometry, so the dashboard is
    however big Neovim has made the window.

    `open = "here"` takes over the WINDOW YOU ARE STANDING IN, which is
    nvdash's arrangement and the default. The buffer that was there is
    remembered along with its view and its window options and put back when
    the dashboard closes, so |:Paseo-buf| is a toggle you can take and leave
    without losing your place; opening a file from the surface simply opens
    the file. `open = "tab"` is the old behaviour: a tab page of its own,
    which costs a tab and leaves the window layout under it intact.

    `chrome` is whether the EDITOR's own tabline and statusline stay up around
    the surface. False -- the default -- hides both while it is open and puts
    them back, whatever they were, afterwards: they are two rows of chrome
    around a surface that has a header and a footer of its own, saying things
    about the buffer this one replaced. Only ever touched for `open = "here"`;
    on a tab page of its own the tabline is how you get back.

    `composer` defaults to a SHARE of the host rather than the float's flat
    seven. This surface is the whole screen -- a fifty-row terminal has forty
    rows of transcript on it and most of them are blank -- and the box you
    type in was still the seven rows it gets in a float over your code.

    `composer_min`, `zindex` and `tab_keys` are read from
    |paseo-config.ui.float| unless you set them here. They describe the
    DASHBOARD -- how short the prompt box rests, how the panes stack, whether
    a bare digit switches tab -- rather than where it is mounted, and two
    copies of one answer is how two surfaces start disagreeing about a
    question neither of them asks differently.

                                                *paseo-config.ui.terminal*
ui.terminal                                                         table

    Terminals -- |paseo-terminals|. Two keys, because a terminal is a SESSION
    on the dashboard rather than a surface of its own.

    `width`, `height`, `row`, `col`, `list`, `zindex` and `backdrop` are GONE
    with the rail-and-pane window they described. A terminal is the size of
    the dashboard, because it is the dashboard. A config still setting them
    is harmless -- nothing reads them.

    `keys` renames or disables the navigation keys: >lua
        terminal = { keys = { next = false, prev = false } }
<
        next      the next session here, prev the previous
        sessions  to the Agents & terminals tab -- the way OUT of a terminal.
                  This was `list`, which meant the rail
        terminal  from the chrome back into the PTY

    All are bound in TERMINAL mode as well as normal, which is what makes
    them worth having and also what takes them from whatever is running
    inside. Right for `claude`, wrong for `tmux`; `false` leaves one unbound.

    `presets` adds entries to what `c` offers, beside the shell and the
    providers the daemon reports. A string is its own command; a table may
    give a `label`, a `command` and `args`. See |paseo-terminals-presets|.

                                                     *paseo-config.ui.answer*
ui.answer                                                           table

    The overlay that answers a question or decides a plan. See
    |paseo-permission-overlay|. >lua
        answer = {
          width = 96,      -- a CAP in CELLS, not a share of anything
          min_width = 54,  -- narrower than this and it leaves the chat window
          backdrop = true, -- dim the conversation behind it
          zindex = 190     -- above everything, deliberately
        }
<
    `width` is cells rather than a percentage, and that is the one thing here
    worth explaining: the overlay does not get a share of the screen, it gets
    whatever the chat window has. So this is a ceiling on that, for the case
    where the chat window is a full-screen dashboard and a 180-column card of
    radio buttons would be absurd.

    `zindex` is the opposite of |paseo-config.ui.float.zindex|, which sits
    below the 50 a float gets by default so that pickers open on top of the
    dashboard. This one is ABOVE everything, because a question you cannot see
    is a turn that never finishes. The card sits 10 above this value and the
    answer box 15.

                                                 *paseo-config.paseo.password*
paseo.password                                            string, unset

    Daemon password, if it has one. A local daemon does not.

                                                              *paseo-no-cli*
The `paseo` CLI is never invoked ~

    Not because it is broken -- `/usr/bin/paseo` is a wrapper that runs the
    Electron binary with `ELECTRON_RUN_AS_NODE=1`, so it is headless, prints
    clean output and its `--json` is parseable. It simply still pays Node
    startup: roughly 1 second against 8ms for the socket. Everything goes over
    `ws://…/ws` through |paseo-bridge| instead, with `GET /api/status` as a
    liveness probe.

    Two executables exist and only one is the CLI:

      /usr/bin/paseo      -> resources/bin/paseo, the CLI. Headless.
      /opt/Paseo/Paseo    -> the desktop app. Opens a window.

    A stale symlink from a CLI-only install can leave the desktop binary
    shadowing the CLI on `$PATH`, which looks exactly like the CLI being
    broken: a window appears and `--json` returns startup logs instead of
    JSON. `:checkhealth paseo` reports which one you have.

                                                     *paseo-daemon-discovery*
Daemon discovery ~

    6767 is the daemon's default port, not a constant, so it is resolved
    rather than assumed. Candidates are tried in order and the first that
    answers wins:

      1. `paseo.url` from |paseo-setup|
      2. `$PASEO_ENDPOINT`
      3. `daemon.listen` in `$PASEO_HOME/config.json` -- the daemon's own
         answer
      4. `127.0.0.1:6767`, ONLY when no config.json named a port

    That last restriction matters. Falling through to 6767 regardless meant a
    config.json naming 6799, with nothing listening there, silently connected
    to whatever was on 6767 -- a different daemon, with different agents,
    reporting success.

    If nothing answers, |paseo-config.paseo.autostart| starts one.

    Each is probed with `GET /api/status`. A `401` counts as REACHABLE: the
    daemon is there and wants a password. Treating it as a miss is how you
    end up reporting "no daemon" about a daemon that is running.

    Only TCP listens can be reached. A `unix:` or `pipe:` listen is a
    different transport and is skipped rather than turned into a URL that
    cannot connect.

    `:checkhealth paseo` prints every candidate and what it answered.

                                                       *paseo-config.voice*
voice                                                               table

    Dictation -- |paseo-dictation|. >lua
        voice = {
          enabled = true,
          key = "<C-t>",   -- in the composer; false to bind nothing
          recorder = nil,  -- nil finds one; a table is a full argv
          rate = 16000     -- what your microphone does well
        }
<
    `recorder` must write RAW PCM16 mono at `rate` to stdout -- headerless,
    no container. That is what the daemon parses; nothing here checks it,
    because nothing can.

    The daemon resamples, so `rate` is about what your microphone does well
    rather than about what the transcriber wants.

                                                 *paseo-config.workspaces.dir*
workspaces.dir                              string, default `".workspaces"`

    Where assembled worktrees live, relative to a project root. Changing this
    is the single knob that moves them out of the project tree. See
    |paseo-workspaces|.

                                       *paseo-config.workspaces.branch_prefix*
workspaces.branch_prefix                           string, default `"ws/"`

    Prefix for the branch a new workspace works on. A manifest carries its own
    `branch_prefix` and that wins; this covers the case with no manifest -- a
    plain git repo, where Paseo cuts the worktree. See |paseo-workspace-kinds|.

                                                *paseo-config.workspaces.open*
workspaces.open                               string|function, default `"tab"`

    What `<CR>` in the workspace picker does. The three strings all switch
    INSIDE this Neovim:

        "tab"   a new tab page, `tcd`'d into the workspace. The default.
        "tcd"   this tab's cwd. No new tab.
        "cd"    the editor's cwd. Everything follows.

    A tab rather than a bare `cd` because chdir'ing in place leaves the
    buffers, LSP clients and jumplist of the workspace you just left pointing
    into it. One tab per unit of work keeps them apart for the price of a tab.

    A function is the escape hatch, and is how you spawn a GUI window per
    workspace instead -- which is what this used to do unconditionally, and
    should not have: over ssh, or in any terminal Neovim, there is nothing to
    spawn and `<CR>` appeared to do nothing. >lua

        open = function(ws)
          if not vim.g.neovide then
            return false  -- decline: the built-in tab switch happens
          end
          vim.fn.jobstart({ "neovide" },
            { cwd = ws.directory, detach = true })
        end,
<
    Returning `false` DECLINES, so one config can spawn a window under a GUI
    and switch in place in a terminal. Any other return value, `nil` included,
    means you handled it.

    To keep the built-in switch and only decide what the new tab SHOWS, leave
    this alone and listen for |paseo-workspace-open-autocmd|.

    An open chat comes WITH you, whichever of the three you pick -- see
    |paseo-chat-follows|. A function that opens its own window does not move
    this Neovim, so the chat in it stays where it is.

                                                  *paseo-config.review.agents*
review.agents                                       boolean, default `true`

    Whether |:Paseo-explain| and |:Paseo-ask| append the other Paseo agents
    working in this tree to the prompt -- their ids, titles, providers and
    status -- so the review agent can call `get_agent_activity` on one and
    report who made a change and what they were told to do. Agents this plugin
    created are excluded: asking the agent you are talking to what it did is a
    loop. Set `false` and the prompt is the reference and nothing else.

                                      *paseo-config.quit.warn_active_agents*
quit.warn_active_agents                             boolean, default `true`

    Warn before a normal whole-editor exit while a non-archived Paseo agent
    session is running, starting, queued, or waiting for attention. The work
    continues on the Paseo daemon; quitting closes only this Neovim client and
    its sidecar. Closing a split, Neovim tab page, or float does not warn.
    Forced `!` exits are the explicit bypass.

    Only asked about a daemon THIS Neovim started. Attaching to one that was
    already running -- the desktop app's, or one from an earlier session --
    costs nothing to leave, and is left alone. See |paseo-quit|.

                                                       *paseo-config.skills.dirs*
skills.dirs                             string[], default `{ "~/.claude/skills" }`

    Where |:Paseo-skills| `install` puts the bundled skills. Absolute; `~` is
    expanded at setup. See |paseo-skills-where| for why the default is a
    global directory rather than a project-local one.

                                               *paseo-config.skills.project_dirs*
skills.project_dirs                       string[], default `{ ".claude/skills" }`

    Relative to the ws project root, for |:Paseo-skills| `install project`.

                                                     *paseo-config.skills.method*
skills.method                                       `"link"`|`"copy"`, default `"link"`

    A symlink keeps this plugin the source of truth, so updating the plugin
    updates the skills with no second step. Defaults to `"copy"` on Windows,
    where symlinks need Developer Mode or elevation -- unless you set it
    explicitly, which is someone who has it and means it.

                                                     *paseo-workspace-kinds*
One intention, three mechanisms ~

A workspace is one unit of work with a working directory. How it gets that
directory depends on what the project is, and |:Paseo-wcreate| decides from
the directory rather than asking you:

    assembled   A plain directory holding several repos. Its worktrees are
                assembled into one composite directory, which Paseo is then
                handed as an ordinary local workspace. This exists because
                Paseo's own isolation needs a git repository and
                `~/Code/openfin` is not one.

                No manifest yet? One is discovered and OFFERED -- the
                dialog at |paseo-ws-dialog| opens on what it guessed, and
                nothing is written until you accept it. Cancelling writes
                nothing and creates nothing.

    worktree    A git repository. Paseo cuts and owns the worktree itself,
                on `branch_prefix .. name`, off whatever is CHECKED OUT.
                Nothing is assembled; there is nothing to assemble.

    local       Neither. A workspace on the directory as it stands, shared
                with anything else pointed at it.

The picker's shape column, and the message after `wcreate`, say which one you
got.

                                                               *paseo-ask-box*
|:Paseo-ask| and |:Paseo-qfask| open a small float, take your question, send
it, and let the chat come up behind the answer. They used to open the entire
chat surface with the reference queued in its composer, which is a lot of
window for one sentence and puts you in the conversation before you have said
anything.

    <CR>        send (normal mode)
    <M-CR>      send (normal or insert). Not <C-s>: see |paseo-chat-keys-send|
    <Esc>, q    cancel, throwing the draft away

An EMPTY box cancels: sending nothing costs a turn and gets you "what would
you like to know?". The box grows with the question, to a cap.

It is a REAL BUFFER, not `vim.ui.input`, for the same reason the composer is
one -- a one-line field throws away your insert-mode keymaps, completion,
abbreviations and undo, and cannot hold a question with a blank line in it.
<CR> is therefore not bound in insert mode; that is how you write a second
paragraph.

|:Paseo-explain| does NOT open the box. It has a question already -- the
rubric -- so there is nothing to type.

                                                                   *paseo-ref*
A REFERENCE IS A LOCATION, NOT A QUOTATION.

|:Paseo-explain|, |:Paseo-ask| and |:Paseo-qfask| send the agent a path and a
line range and let it open the file. They used to paste the lines in. That
made the prompt scale with the size of whatever you asked about -- and the
worst case is not a long hunk, it is a NEWLY CREATED FILE, which gitsigns
reports as one all-added hunk and which therefore pasted the file in whole.
Reading also gets the agent the file's current state and the lines around it,
where a paste is a snapshot from when you pressed the key.

The path it is told to open is ABSOLUTE, and that is not cosmetic. A ref's
`path` is relative to the WORKSPACE so it disambiguates across member repos
(`clm_api/app/main.py`), while `root` -- the agent's cwd -- is the member
worktree. Resolve one against the other and you get
`.../clm_api/clm_api/app/main.py`. While the code was inlined the path was
only a label and nobody noticed; the moment the agent has to open it, it has
to be absolute.

ONE CARVE-OUT: a pure deletion. Its lines are not in the file to read, and a
deletion's line number is the line ABOVE the removed block, so "go and read
it" would show the agent the code that SURVIVED and get a confident answer
about the wrong lines. Those hunks are still quoted, fenced as `diff`, and
labelled so the agent does not go looking for them.

If the buffer has unsaved changes the reference says so, since the agent reads
disk and you are looking at the buffer.

                                                                  *paseo.Repo*
A repo is: >lua
    {
      name     = "clm_api",                     -- which repo this is
      worktree = "/home/you/Code/openfin/clm_api",
      gitdir   = "/home/you/Code/openfin/clm_api/.git",
    }
<
`name` comes from the common git dir, not the worktree's basename. A linked
worktree is named after the workspace ("otp-rate-limit"); what a picker row
needs to say is which repo it is.

`gitdir`, conversely, is `<repo>/.git/worktrees/<name>` for a linked worktree
rather than the common dir. That is also deliberate: it is per-worktree, which
is what identifies the member.

7. PASEO GLOSSARY AND WORKSPACES                            *paseo-workspaces*
                                                               *paseo-glossary*

These names follow Paseo's model:

    Project        The long-lived codebase Paseo knows. Contains workspaces.

    Workspace      One unit of work in a project, with a working directory.
                   Contains agent sessions and terminals.

    Agent          The AI worker identified by an agent ID.

    Agent session  One agent's state and timeline inside a workspace. Several
                   can share the same workspace and files. Bare `session` is
                   retained only in compatibility aliases and stable internal
                   module or protocol names.

    Tab            A Paseo UI surface presenting an agent session. It is NOT a
                   Neovim TAB PAGE. The dashboard sections are UI tabs too;
                   neither kind is an isolation boundary.

    Dashboard      paseo.nvim's full-screen surface: six tabs, the session
                   strip and the panes. One thing, on one of two MOUNTS.

    Mount          Where the dashboard is drawn -- `float`, over your code, or
                   `buffer`, in a window of its own. Same chrome, same tabs,
                   same keys; only the window differs. See |paseo-chat-float|
                   and |paseo-chat-buffer|.

    Sidebar        The narrow surface beside your code. A DIFFERENT surface
                   from the dashboard, not a third mount of it.

    Terminal       A daemon-owned PTY in a workspace. It appears beside agent
                   sessions but is not an agent.

    Worktree       A Git checkout used to isolate a workspace. It is a
                   mechanism, not a synonym for workspace.

    Daemon         The background Paseo process that owns projects,
                   workspaces, agent sessions, timelines, and terminals.

    Provider       The agent backend, such as Claude, Codex, or OpenCode.

    Model          A provider-specific model used by an agent.

    Subagent       An agent created or coordinated by another agent.

    Fork           A new agent session initialized from a source agent's
                   conversation snapshot. paseo.nvim currently puts it in a
                   new workspace.

Isolation is a property of the WORKSPACE, not of the agent session. Two agent
sessions in one workspace edit the same files, deliberately -- that is what
makes "an agent writing code and another reviewing its diff" work. Two
workspaces are isolated only when each has its own worktree.

                                                      *paseo-workspaces-source*
Paseo is the source of truth. A workspace created in the Paseo app, or by
`paseo workspace create`, appears here exactly like one this plugin assembled.
What this plugin adds is the thing Paseo cannot know: that a directory is
SEVERAL worktrees rather than one checkout.

                                                       *paseo-workspaces-multi*
That matters because `--isolation worktree` requires a git repository. A
project like `~/Code/grasslabs/kora` is a plain directory holding five repos,
so Paseo cannot isolate it -- every workspace on it points at the same
checkout. |paseo-ws-assembly| fills that gap: N worktrees assembled into one
directory, which is then handed to Paseo as an ordinary local workspace.

                                                        *paseo-ws-assembly*
Assembly ~

A workspace this plugin assembles is a directory: >
    <project>/.workspaces/<name>/
    ├── clm/        a worktree of <project>/clm, on ws/<name>
    ├── clm_api/    a worktree of <project>/clm_api, on ws/<name>
    └── Docs/       a symlink to <project>/Docs, shared
<
It is driven by `<project>/.ws/workspace.toml`, which |:Paseo-ws| generates.
Without a manifest, creating a workspace just registers the directory with
Paseo -- which is the right behaviour for an ordinary single-repo project,
where Paseo's own worktree isolation already works.

                                                          *paseo-ws-dialog*
Configuring the manifest ~

Discovery can work out nearly all of a manifest by looking at the project. Two
things it cannot: WHICH BRANCH each repo should be based on, and WHICH of the
directories sitting beside your repos are shared context rather than junk that
happens to be there. Those are the two it asks about, and it asks on a screen.

|:Paseo-wcreate| in a multi-repo directory with no manifest opens it, and so
does |:Paseo-ws| `init`: >

    󰙅  Workspace                              ~/Code/openfin

     󰳏  Repos   m                  󰉋  Shared   s
      ■  clm                dev     ■  Docs
      □  clm_api            dev     □  test quotes
      ■  fos-pwa            dev     □  test-s3

     c  write the manifest             2 repo(s), 1 shared
<
    <CR>      include this repo / keep this sibling
    b         set the focused repo's base branch
    t         edit the whole file as TOML instead
    c         write it
    q         cancel -- and NOTHING is written

Each repo carries its base branch on the right of its own row, and whatever
discovery could not decide about it appears under the card as you move. An
unchecked repo becomes `default = false`; an unchecked sibling is dropped from
`shared`.

Cancelling writes nothing and creates nothing. A half-decided manifest is
worse than none, because the project would answer "assembled" from then on and
never ask again.

                                                       *paseo-ws-dialog-again*
Opening it on a project that already has a manifest LOADS that manifest rather
than replacing it, and a sibling you pruned stays pruned even though it is
still sitting there on disk. That is the whole point: the generated file used
to say `PRUNE THIS` in a comment, and nothing that re-read the project ever
honoured the answer.

                                                      *paseo-workspaces-grouping*
Grouping ~

The sidebar and the picker nest a workspace under the project it LIVES IN,
which is not always the project Paseo has it filed under.

An assembled workspace is a plain directory -- it has to be, because a git
worktree is per repo and a unit of work spanning four repos has nowhere else
to live. So it is not a git repo, and when the daemon is asked to open
`~/Code/openfin/.workspaces/billing` it registers that directory as its own
TOP-LEVEL project called `billing`, a sibling of `openfin` rather than
something inside it.

The shape is recognisable from the path alone -- some ancestor's parent is
|paseo-config.workspaces.dir| -- so the editor groups on that. Nothing is
renamed and nothing is migrated: the daemon's own record is left exactly as it
is, and a workspace made in the app lands in the same group as one made here.

                                                       *paseo-workspaces-panel*
On the Workspaces tab (`6`) ~

Each group is a heading with a hairline under it, and its workspaces below
that. The rule is there because a swatch and a blank line alone read as one
list that happens to have headings in it, rather than as one group per
project.

EVERY ROW SAYS WHAT IT IS DOING, in the first cell, from the same glyph
registry the timeline's tool cards use: >

     ⠙  something in this workspace is working, right now
     󰀦  something needs you -- a permission, a question
     󰗠  opened, and nothing running in it
     󰄰  you have never started an agent here
<
Only the first of those moves, and only while something is actually running --
a timer that repaints a tab nobody is looking at is a leak, and the two
finished states say all they have to say standing still.

Two destructive acts, deliberately in different places because they are not
two strengths of one thing:

    <CR>            open a chat on the workspace under the cursor
    d               archive it. Retires that unit of work, and takes its
                    worktrees and their `ws/<name>` branches with it. Refuses,
                    and says what it would lose, if a member holds work that
                    exists nowhere else
    x               forget the project the cursor is in -- from the heading or
                    from any workspace under it. Drops PASEO'S RECORD of a
                    directory tree, never the files. This is how you get rid
                    of the top-level project the daemon invented for a
                    `.workspaces/<name>` directory. A group can span several
                    such records; it removes all of them, and says how many
                    before it does

Two keys rather than one that decides from the line you are on: archiving
retires a unit of work and forgetting drops a record of a whole tree, and one
key for both is the shape of a mistake. Both confirm first.

With the pointer, the same two are offered on the row and on the heading --
under the pointer only, because a column of destructive glyphs down the side
of a list is a column of mistakes.

                                                          *paseo-workspaces-keys*
In the workspace picker (|:Paseo-workspaces|) ~

    <CR>      open it -- a new tab page `tcd`'d into the workspace, or
              whatever |paseo-config.workspaces.open| says. An open chat
              follows: |paseo-chat-follows|
    <C-s>     its agent sessions
    <C-n>     create a workspace
    <C-d>     archive it -- refuses, and says what it would lose, if a member
              holds work that exists nowhere else. Its worktrees and their
              `ws/<name>` branches go with it
    <C-r>     review it here: `tcd` into the workspace so the repo list widens
              to every member, then fire |paseo-review-autocmd| -- what
              "review" means is your config's to say

In the agent picker (|:Paseo-agents|; |:Paseo-sessions| is an alias) ~

    <CR>      open a chat on that agent session, with its history
    <C-n>     start a new agent session in this workspace
    <C-y>     copy the complete agent ID
    <C-d>     archive that agent session

8. GIT                                                             *paseo-git*

`paseo.git` is the only module that shells out to git, and together with
|paseo.repos.list| it is THE PUBLIC DATA LAYER your review workflow is built
on. It has no UI in it and never opens a window: the changed-files picker, the
hunk quickfix list and the staging keymap live in your config now, and these
four functions are what they call.

Two types flow through it.

                                                                *paseo.Change*
A changed file: >lua
    {
      repo      = <paseo.Repo>,
      path      = "app/main.py",              -- relative to repo.worktree
      orig_path = nil,                        -- rename source, when there is one
      index     = "M",                        -- X of the XY status code, "?" untracked
      worktree  = " ",                        -- Y of the XY status code
      untracked = false,
    }
<
                                                                  *paseo.Hunk*
One hunk of one file: >lua
    {
      repo         = <paseo.Repo>,
      path         = "app/main.py",
      lnum         = 42,                      -- see hunks() below
      added        = 7,
      removed      = 2,
      kind         = "change",                -- add | change | delete | new
      file_deleted = false,                   -- the whole file is gone
      lines        = { "@@ -40,2 +42,7 @@", "-old", "+new" },
    }
<
`lines` is the hunk verbatim -- its `@@` header, its `-`/`+` body, and any
`\ No newline at end of file` marker. That is what `stage()` applies, so it
has to survive intact if you pass hunks around.

                                                            *paseo-git-status*
require("paseo.git").status({repo})                    -> |paseo.Change|[]

    Every changed file in one repo -- staged, unstaged and untracked -- in one
    pass, sorted by path. Ignored files are never included.

    Reads `--porcelain=v2 -z`, whose rename records are a PARSING TRAP: a `2 `
    record is TWO NUL-terminated fields, the record and then `origPath`, so a
    naive split on NUL reads the rename source as the next record and desyncs
    everything after it. This handles that; a parser of your own must too.

                                                             *paseo-git-hunks*
require("paseo.git").hunks({repo}, {changes})            -> |paseo.Hunk|[]

    Every hunk, as quickfix-ready positions. {changes} restricts it to those
    files; omitted, it covers the whole repo.

    `-U0` IS PART OF THE CONTRACT. A hunk header's line numbers only delimit
    the hunk itself at zero context, so `lnum` is only meaningful there -- ask
    git for context elsewhere and reuse these numbers and you are off by the
    context width.

    For a deletion, `@@ -a,b +c,0 @@` gives `lnum = c` -- NOT `c + 1` --
    because `gitsigns.stage_hunk()` acts on `added.start`, and for a pure
    deletion that is the line ABOVE the removed block. A deletion at the top of
    a file yields `c = 0` and clamps to 1. A hunk header also OMITS a count of
    1: `@@ -2 +2 @@` means `-2,1 +2,1`, and reading the missing count as 0
    turns every single-line change into a phantom deletion.

    Untracked files never reach `git diff`; each becomes one synthetic
    `kind = "new"` entry.

                                                         *paseo-git-diff_text*
require("paseo.git").diff_text({change}, {opts})             -> string[]

    The diff of one file, for a previewer. Working tree against `HEAD`, so
    staged and unstaged changes appear together -- which is what you are
    reviewing. `opts.context` defaults to 3.

    An untracked file has no `HEAD` side and goes through `--no-index` against
    /dev/null, which exits 1 BY DESIGN ("the files differ"). This handles that;
    a previewer that shells out directly must too, or every new file previews
    as an error.

                                                             *paseo-git-stage*
require("paseo.git").stage({hunk}, {callback})

    Stages one hunk, and needs no buffer to do it. {callback} receives an error
    string or nil.

    It applies a reconstructed patch with `git apply --cached --unidiff-zero`
    rather than driving `gitsigns.stage_hunk()`, for two reasons found in
    testing. THE RACE: staging from a list means opening the file first, and
    gitsigns attaches asynchronously -- called straight after `:edit` it finds
    no cache for the buffer and returns SILENTLY. Four of six hunks vanished
    that way. THE BUFFER: staging from a list should not drag a window onto a
    file you were only reading about.

    A WHOLE-FILE DELETION (`hunk.file_deleted`) has no file on disk, so no
    buffer can open on it and gitsigns can never attach. Those, and untracked
    files, go through `git add` instead, which records a removal correctly.

                                                          *paseo-chat-follows*
THE CHAT FOLLOWS THE WORKSPACE YOU ARE IN.

Switching workspace (|paseo-workspaces-keys|) re-points an OPEN chat at the
agent in the workspace you just moved to. Without it the full-screen surface
-- the one window on screen -- went on describing the workspace you had just
left, and because a float belongs to the tab page it was opened on, the
default `"tab"` switch did not even leave it visible.

Three things it deliberately does not do:

  - It does not OPEN a chat. Changing directory is not a request for one, so
    with nothing on screen nothing happens.
  - It does not ask which provider to use. A workspace you have not started an
    agent in yet says so and waits; `:Paseo chat` is how you start one.
  - It does not move your cursor out of your code. The full-screen surface
    takes focus, because it covers the screen and you need to type into it;
    the sidebar does not.

`<C-r>` re-points the chat too, but never takes focus -- the cursor belongs in
whatever |paseo-review-autocmd| opens.

AND WHEN YOU OPEN THE CHAT AFTERWARDS instead, `:Paseo chat` resolves the
directory you are STANDING IN -- the workspace containing the cwd, else the
repository containing it, else the cwd itself. It used to read the git
toplevel of the BUFFER, with the cwd reached only for an unnamed one, and
that is what made switching workspace and then opening the chat show you the
workspace you had just left: with `workspaces.open = "tcd"` the switch reuses
the tab, so the file you had open in the old worktree is still the current
buffer.

`:Paseo ask`, `:Paseo explain` and everything else that means a particular
FILE still resolves from that file. Only "open the chat", which means "here",
reads the cwd.

                                                        *paseo.ui.chat.follow*
require("paseo.ui.chat").follow({root}, {opts})              -> boolean

    Re-point the open chat at `root`. Returns false when no chat is on screen
    -- having dropped the plugin's idea of which chat is CURRENT, so that the
    next `:Paseo chat` resolves where it is from scratch rather than reopening
    the workspace you just left. `opts.focus` overrides the rule above.

                                                 *paseo-workspace-open-autocmd*
Opening a workspace (|paseo-workspaces-keys|) fires `User PaseoWorkspaceOpen`
after the `tcd`, with the root in `data.root`. That is the seam for deciding
what the new tab SHOWS -- a file picker, oil, a dashboard -- without replacing
the switch itself: >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "PaseoWorkspaceOpen",
      callback = function(ev) require("oil").open(ev.data.root) end,
    })
<
It does NOT fire when |paseo-config.workspaces.open| is a function that
handled the open itself -- that function already knows where it sent you.

                                                         *paseo-review-autocmd*
The workspace picker's `<C-r>` (|paseo-workspaces-keys|) does not build a list
itself. It `tcd`s into the workspace, invalidates the repo cache, and fires: >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "PaseoReview",
      callback = function(ev)
        -- ev.data.root is the workspace directory
      end,
    })
<

9. THE AGENT BRIDGE                                             *paseo-bridge*

Agents are reached through a sidecar: `sidecar/paseo-bridge.ts`, one Bun (or Node
>= 22) process per Neovim session, holding one WebSocket to the daemon and
speaking newline-delimited JSON over stdio. Its operations live in the
`sidecar/bridge-*.ts` modules.

It is not the `paseo` CLI because that boots Electron per invocation and costs
about 2.4 seconds. It is not a raw WebSocket in Lua because the frame codec is
the easy part: the real surface is subscriptions with server-issued IDs,
snapshot-then-update ordering, timeline epochs and cursors, `replacement`
invalidation and `subscription_restored` after reconnect.

                                                          *paseo-bridge-agent*
Review agents are reused when their directory and `paseo.nvim = review` label
match. When |paseo-config.paseo.provider| names a provider/model, both must
match too. If no agent matches, the new-session review presents the daemon's
mode, model reasoning, and feature choices before creation.

                                                       *paseo-bridge-lifetime*
The sidecar starts on the first request that needs it and is stopped on
`VimLeavePre`. Agents it created keep running on the daemon and stay visible in
Paseo; closing Neovim does not archive them.

10. THE CHAT WINDOW                                              *paseo-chat*

Three surfaces onto one conversation. `:Paseo chat` toggles whichever one
`ui.surface` names, and that is the FULL SCREEN one by default: it is the
surface with everything on it, and the sidebar is what you switch TO.

                                                         *paseo-chat-sidebar*
The SIDEBAR is a pane on the right: the conversation above, the composer
below -- `:Paseo sidebar`, or `<C-f>` from the dashboard. Narrow, beside your
code, for when the conversation is a thing you glance at rather than the thing
you are doing.

                                                          *paseo-chat-header*
The header ~

The row ABOVE THE BOX YOU TYPE IN, drawn by both surfaces from one builder so
they cannot disagree about which mode the session is in. It says what the
session IS: >

    ─ claude/sonnet-5 · acceptEdits · 󰧑 think · ⚡ · ~/Code/kora ── ⠹ 14s ─ 󰌑 send ─
<
A pending permission shouts from here -- `` needs you`` -- because then the
agent is not working, it is waiting for YOU.

It used to live at the far TOP of the screen -- a winbar over the transcript in
the sidebar, the first row of the chrome on the dashboard -- which is as far
from the cursor as that screen goes. You decide what to type with these facts
and you decide it while looking at the composer, so they belong against the
composer. It doubles as the box's title row, which is what lets the box drop
its drawn border and become a plate like every other card; see
|paseo-chat-composer|.

IT IS ONLY EVER THIS ROW. The dashboard used to repeat it in the chrome above
the tab bar on every tab but `Chat`, which said what the bar over the box
already says and cost those five tabs a row: the tab bar, the strip and the
whole panel below them all sat one row lower than on `Chat`, so changing tab
shifted the layout under you. The panel that can change any of these facts is
|paseo-chat-settings|, which is tab `3`.

IT DEGRADES BY DROPPING WHOLE FACTS rather than by cutting the row. A sixty
column sidebar cannot say all of it, and truncation takes the RIGHT -- which is
where the working directory is. So it gives up what it can spare, cheapest
first -- the feature toggles, then the thinking level, then the context
figure, then the model -- and keeps the mode and the directory: >

    ─ Plan Mode · paseo.nvim   ⠹ 1m 12s ─ 󰌑 / Alt + 󰌑 send ─
<
Shortening is tried only once there is nothing cheaper left to drop:
`~/Code/paseo.nvim` beats `paseo.nvim`, and `paseo.nvim` beats no directory at
all. Nothing outranks a pending permission, which is never dropped at any
width.

                                                            *paseo-chat-rule*
THE ROW IS ALSO THE BOX'S TOP EDGE. Without a frame the composer was a slab of
card colour with a row of text on it, and on a theme whose elevation tiers sit
close together that is not a box -- it is the same screen, slightly different.
A rule of its own would cost a row of the transcript to say something true the
whole time, so the bar IS the rule: it starts and ends on a hairline, the gaps
between its clusters are drawn in it, and the words sit on it the way a title
sits on a frame. `PaseoComposerBorder` is the group, because that is what it
is now.

                                                          *paseo-chat-status*
The status ~

What the turn is DOING -- a spinner and how long it has been running -- is on
the RIGHT-HAND END OF THE SAME ROW, on top of the box: what you are waiting for
is the answer to whatever is in it. >

    ─ claude/sonnet-5 · acceptEdits · 58% left · ~/Code/kora ── ⠹ 28m 49s ─ 󰌑 send ─
<
The count is the point. A static dot looked the same at two seconds and at two
minutes, so a wedged turn and a working one were the same picture and the only
way to tell was to open the app.

It is HUMANISED for the same reason: `1729s` is arithmetic homework, `28m 49s`
is a duration. Past an hour the seconds are dropped (`1h 24m`) -- at that scale
they are noise, and dropping them stops the field growing a third segment that
shifts everything beside it.

It is given a FIXED-WIDTH slot, ten columns whether it needs them or not. That
is the answer to the reason this used to live at the bottom of the screen: it
is the one field on the row that changes ten times a second, and among static
ones it pushed everything beside it sideways every time the count gained a
digit. In a slot of its own it cannot.

The dashboard's footer keeps a copy for the tabs that have NO composer on them.
A turn runs on while you read the Changes panel, and that is exactly when "is
it still going" is hard to answer -- nothing else on those tabs moves.

                                                              *paseo-chat-left*
HOW MUCH CONTEXT IS LEFT sits in the same row, once the daemon has reported any
usage: >

    58% left
<
It says what is LEFT, not what is spent. It used to be a bare `42%`, which said
neither what the number counted nor which way it ran -- and it counted the
fraction USED, so the figure you watched climbing was the one you wanted to
watch falling.

NO BAR BESIDE IT. There was a six-cell gauge here, and a gauge earns its place
by being readable at a glance in a way a number is not -- which is true on the
Usage panel, where it sits in a card with room to be a real readout, and false
in six cells wedged into a row of text: the difference between 58% and 71% was
two glyphs, in a row you are scanning for words. The pressure colour went with
it, for the same reason a number that changes colour in a row of dim text is a
twitch rather than a warning. |paseo-chat-usage| is where a context window in
trouble is worth looking at.

                                                           *paseo-chat-float*
The DASHBOARD on its FLOAT MOUNT -- the DEFAULT -- is `:Paseo chat`,
`:Paseo dash`, or `<C-f>` from the sidebar. The same conversation, under the
same header, plus a tab for every other thing Paseo knows: >

    1 Chat                  the conversation and composer
    2 Agents & terminals    the agents AND terminals here, live -- open one
    3 Settings              mode, thinking level, model and feature toggles
    4 Changes               what is changed on disk -- open one
    5 Usage                 context window, tokens, cost and what is left
    6 Workspaces            every workspace, and this unit of work's repos
<
`1`-`6` jump, `<M-1>`-`<M-6>` and `<Tab>`/`<S-Tab>` do the same, and
everything on screen that does something responds to a CLICK as well -- the
tab bar, a mode, a model, a session, a changed file. The keys are bound on the composer
and the conversation as well as on the chrome, because the Chat tab puts your
cursor in the composer, and a key bound only to a window you are never in is a
key that does not work.

                                                          *paseo-chat-buffer*
The DASHBOARD on its BUFFER MOUNT is the same dashboard in a real WINDOW --
`:Paseo buf`, or `ui.surface = "buffer"`. Same chrome, same six tabs, same
panes, same keys; the difference is only which window it is mounted on. It
takes over the window you are standing in, hides the editor's tabline and
statusline, and fills what is left, so it gets the whole screen rather than
the 94% a centred float leaves itself.

That is nvdash's arrangement, and |:Paseo-buf| is a TOGGLE: press it again and
the file comes back, on the line you left it on, with that window's own
'number', 'wrap' and highlights. The surface is one window, and the key that
took the window is the obvious way to give it back.

It used to open on a tab page of its own, and the tab bought nothing: a tab is
an arrangement of WINDOWS and this is one of them. It put a tabline up over a
surface that draws a header of its own, and it made "back to my code" a `gt`
rather than the key that opened it. |paseo-config.ui.buffer| `open = "tab"` is
the old behaviour, and `chrome = true` keeps the tabline and statusline up.

OPENING A FILE TAKES IT DOWN. That is half of what the surface is, and it does
not happen by itself: the cursor here is in the composer, which is a FLOAT, so
a picker that opens a file in "the window you came from" would put somebody's
source in a three-row box over a dashboard that is still up. A real file
landing in either pane is taken as "leave" and is reseated in the window the
surface borrowed -- which is where it was always going.

The chrome is an ordinary window holding an ordinary buffer with a filetype of
its own -- `paseo-dash`, the thing to hang an `ftplugin/paseo-dash.lua` off,
the way you would for a file tree. The conversation and the composer are
floated over it and ANCHORED to it, which is what makes them follow it when a
split moves it and what keeps them on its tab page rather than on whichever
tab you happened to be standing on.

`q` closes it and hands the window back. `<Esc>` does NOT, unlike on the
float: a float is a thing in front of you and `<Esc>` is how you dismiss it,
but this is a place you are standing, and one stray `<Esc>` after a mistyped
`i` should not take the surface down. Closing the window yourself -- `:q`,
`<C-w>c`, `:tabclose` -- closes the surface with it.

`<C-f>` IS NOT BOUND HERE. That key names one swap, between the sidebar beside
your code and the float over it, and this surface is neither of those things:
it is a place of its own. Use |:Paseo-dash| or |:Paseo-sidebar| to move.

All three surfaces share the same buffers, so switching preserves your draft
and your scroll position.

                                                           *paseo-chat-usage*
The USAGE tab (`5`) answers two different questions, from two different
places.

The top is about THIS SESSION: how full the context window is, and what the
last turn cost. That rides the agent snapshot and needs no polling. A tile is
drawn only when it has a figure -- an empty card is not information, it is a
box taking up a third of the row to tell you nothing.

The tokens and the dollar figure arrive ONLY on turn completion, and the
daemon does not keep them: the provider's streaming usage update carries the
context window and nothing else, and it REPLACES the snapshot's copy rather
than merging into it. So the plugin keeps the last complete turn itself, and
the tile says `Last turn` when that is what you are looking at.

The bottom is about the ACCOUNT -- `Plan limits`. ONE card, for the provider
this session is on, headed with the plan name, with a bar per window: >

    Claude  Max 20x
      Session   23%   resets in 2h 14m
      Weekly    91%   resets in 3d 4h
<
Only this session's provider, not every provider the daemon can authenticate:
a wall of quotas for providers you are not using is neither the question you
asked nor affordable in rows -- the body of a panel is truncated rather than
scrolled. Switching model on the Session tab switches the card.

`claude` reports a five-hour window, a weekly one, and a weekly window per
scoped model; `codex` reports a session window, a weekly one, a code-review
window and a credit balance. A provider with no quota fetcher in the daemon --
`fable` and `gemini` have none -- says so rather than leaving a gap, and one
you are not signed in to shows what the daemon said about it.

The numbers are the daemon's cache of the provider's own usage endpoint, not a
poll: the panel asks once when you open it.

                                                         *paseo-chat-session*
The SETTINGS tab (`3`) is the one you drive from the keyboard. Every setting
this session has is on it at once, grouped into cards, with what is currently
set filled in rather than marked with a dot: >

    ╭─ Permission mode   m  ──────────────────────────────╮
    │   Plan   Always ask   Accept edits   Bypass         │
    │  Edits are applied without asking.                  │
    ╰─────────────────────────────────────────────────────╯

    ╭─ 󰧑  Thinking   t  ────────╮  ╭─ ⚡  Features   f  ───╮
    │   Off   Think             │  │    Fast mode         │
    ╰───────────────────────────╯  ╰──────────────────────╯

    ╭─ Model   s  ────────────────────────────────────────╮
    │  ● Opus 5                                  default  │
    │  ○ Sonnet 5                                         │
    ╰─────────────────────────────────────────────────────╯
<
    h j k l   move to the next setting -- all four directions do, and
              running off the end of a card lands on the next one
    <CR>      apply what is focused (a Features entry toggles)
    m t f s   jump to Mode, Thinking, Features or Model; the letter is
              printed on the card so the key is where you are looking
    r         re-ask the daemon

A click does the same thing, and pointing at a setting lights it exactly as
moving to it does -- hover and focus are the same paint, because they are the
same state.

`bypassPermissions` is drawn in red and `acceptEdits`-style modes in amber.
Until now every mode was the same colour, which made "nothing asks, everything
runs" look identical to "research and write a plan".

The description under a card belongs to whatever is FOCUSED, not to every
row -- one line that changes as you move, rather than five stacked lines you
read once and then scroll past.

On a short editor the cards drop their internal padding so the whole thing
still fits; the layout is measured before it is drawn, not guessed at.

                                                       *paseo-chat-settings*
The same four cards open on their own, centred, without the dashboard: >

    :Paseo mode          the permission modes
    :Paseo thinking      the reasoning levels
    :Paseo switchmodel   the models
    :Paseo agent-settings  all of them (`session` is a compatibility alias)
<
Same keys, plus `q`/`<Esc>` to close. These used to be `vim.ui.select` lists
of strings with a `●` glued to the front of one of them; they are the Settings
tab's renderer in a window of its own, so there is no second implementation to
drift.

                                                       *paseo-new-session*
WHERE THERE IS NONE, and nowhere else. `:Paseo chat` asks the daemon what is
already running in this directory first, and opens that -- INCLUDING a session
you started in the Paseo app, which carries none of this plugin's labels. It
used to look only for sessions this plugin had created, on the model
|:Paseo-model| was set to, so opening the chat in a workspace with two live
tabs in it offered to start a third. Preference order: ours on that model,
ours on any model, anyone's on that model, anyone's -- and within each,
whichever was touched most recently.

The screen below is what you get when the answer really is nothing. It TAKES
THE CURSOR when it opens, and keeps it: it is asking you a question, and the
surface underneath re-fitting itself used to pull the cursor back into the
composer and leave you clicking the modal to answer it.

Starting an agent where there is none opens the SAME renderer over an agent session
that does not exist yet -- two more cards, because provider and model are
settings here and are not settings on a running agent: >

    ╭─ 󱚠  Provider   p  ────────────╮  ╭─ Permission mode   m  ─────────╮
    │   Claude   Codex              │  │   Plan   Always ask   Bypass   │
    ╰───────────────────────────────╯  ╰────────────────────────────────╯

    ╭─ Model   s  ──────────────────────────────────────────────────────╮
    │  ● Opus 5                                                default  │
    │  ○ Sonnet 5                                                       │
    ╰───────────────────────────────────────────────────────────────────╯

    ╭─ 󰧑  Thinking   t  ────────────╮  ╭─ ⚡  Features   f  ────────────╮
    │   Off   Think                 │  │    Fast mode                   │
    ╰───────────────────────────────╯  ╰────────────────────────────────╯

     c   create agent                                  claude/opus-5

     h j k l  move   ⏎  apply   p s m t f  group   r  reload   c  create
<
`c` creates, `q` cancels, and nothing is created until you press one. There is
no Create card, because a card that is not a setting reads as one.

The SCREEN IS THE PICKER. Choosing a provider used to be two `vim.ui.select`
prompts before you saw anything, and what you saw afterwards was a plain
buffer -- `Provider        Claude` -- with no highlights and another
`vim.ui.select` behind every row. A daemon with no provider ready still
reports that as an error rather than opening an empty window.

Changing provider, model or mode re-asks the daemon what FEATURES that
combination supports, because they are per model and per mode both. The card
keeps the height it had while that is in flight, so the ones below it do not
jump; and a reply for a choice you have since changed is dropped rather than
applied, which is what two quick mode changes used to produce.

`:Paseo fast` stays a direct toggle rather than a window -- it is a one
keystroke convenience and putting a window in front of it would defeat the
point. It opens the Features card only when this provider has no `fast_mode`
to toggle.

                                                               *paseo-fork*
Forking an agent session ~

Press `f` in normal mode in either chat buffer. The daemon snapshots the
COMPLETE conversation available at that moment; no cursor or message boundary
is sent. After a workspace name and multiline first prompt are entered, the
plugin creates the appropriate assembled/worktree/local workspace and creates
the new agent with the first prompt and `chat_history` attachment in one
request. Provider, model, permission mode, thinking level, and supported
features come from the source.

Nothing is created if either prompt is cancelled. A daemon without the
`agentForkContext` capability is rejected before creation. If agent creation
fails after workspace creation, the empty workspace is retained and named in
the error rather than being deleted automatically.

Changing a live model asks whether to `Fork into a new workspace`, `Use for
this agent's future turns`, or `Cancel`. A model fork leaves the source
untouched and keeps only settings supported by the target model, using target
defaults for the rest.

Same-workspace “Fork in a new tab” is intentionally deferred: Paseo tab and
Neovim tab page are different concepts and that presentation is not yet
decided.

                                                    *paseo-cross-agent-prompt*
Cross-agent communication ~

On `Agents & terminals`, `y` copies the selected agent's complete ID to the
unnamed register and the system clipboard when available. In the agent picker,
use `<C-y>`. Paste that receiving ID into the sending agent's chat and ask it
to use Paseo's cross-agent prompt tool. Terminal rows do not offer this action.

                                                          *paseo-chat-zindex*
On the buffer surface the chrome is a normal window, which is below every
float whatever number anyone writes -- and its panes keep the same
`ui.float.zindex` + 5 the dashboard uses everywhere, so pickers, previews and
the permission dialog stack over it exactly as they do over the float.

The dashboard sits BELOW the z-index a floating window gets by default, at
`ui.float.zindex` -- 30 against 50. That is deliberate: a telescope picker, a
diff preview or a `vim.ui.select` opened from the dashboard has to render ON
TOP of it, and at the z-index this used to use they rendered underneath and
looked like nothing had happened. The one window exempt from this is the
permission dialog, which asks for a z-index above everything, because it is
the one window that must not be covered.

                                                          *paseo-chat-keys*
In the composer ~

    <CR>      (normal mode) send
    <M-CR>    send, from normal or insert mode. NOT <C-s>: that is the
              session list, here as everywhere else -- see |paseo-chat-keys-send|
    <C-CR>    the same, where the terminal can send it
    <C-s>     the session list
    p  P      paste -- an image if the clipboard has one, text otherwise
    1-6       jump to a tab (full screen; see ui.float.tab_keys)
    <M-1>..6  the same, without taking the count keys
    <Tab>     next tab, <S-Tab> the previous one
    <C-f>     switch surface -- float <-> sidebar. Not bound on the buffer
              surface; see |paseo-chat-buffer|
    <C-c>     stop the turn -- normal or insert. See |paseo-chat-stop|
    <C-t>     speak instead of typing. See |paseo-dictation|
    q         close the chat

The box is the size of what is in it: |paseo-config.ui.sidebar| `composer` is
a ceiling it grows to and `composer_min` the floor it rests at, not a fixed
height.

In the conversation ~

    <Tab>     expand or collapse the item under the cursor
    <CR>      the same
    1-6       jump to a tab (full screen; see ui.float.tab_keys)
    <M-1>..6  the same, without taking the count keys
    gp        reopen a pending permission prompt
    f         fork the complete conversation into a new workspace

    <C-c>     stop the turn. See |paseo-chat-stop|

On the Settings tab ~

    h j k l   move between settings
    <CR>      apply the focused setting
    m t f s   jump to a group of settings

                                                         *paseo-chat-lists*
On the SESSIONS, WORKSPACES and CHANGES tabs ~

Three lists, one set of keys, because they are one kind of screen: >

    j k       move -- <Down> and <Up> too
    h l       the previous or next SECTION
    g G       the first or last row
    <CR>      open what is focused
    r         re-fetch
<
Plus, per tab: >

    Sessions     c  new terminal     a  new agent
                 R  rename a terminal
                 d  kill a terminal, or archive an agent -- asked first
    Workspaces   n  new here         o  the full picker
                 d  archive -- asked first, and by name
                 x  forget the project this row is in -- see below
<
`r` is re-fetch on ALL of them, and on the Settings tab, which is why rename
is `R`: one key meaning "ask the daemon again" on five tabs and "rename this
terminal" on the sixth is the kind of near-miss that makes one surface feel
like several. A key the panel claims for itself wins over the built-in, binds
once, and the hint bar says which -- a bar advertising one key for two things
is wrong about the first of them.

THE FOCUSED ROW IS PAINTED, in the same colour hover uses: pointing at a row
and moving to it are the same state. Arriving at a tab puts focus on a row --
the one you are in, else the first -- so the first `<CR>` does something.

                                                        *paseo-chat-gutter*
WHERE THE CURSOR IS AND WHICH ONE IS OPEN ARE TWO DIFFERENT MARKS. The focus
band is one flat sweep across the row, so "this is the session you are in" --
which used to be a coloured bar and a coloured title INSIDE that sweep -- said
nothing the moment you pointed at the row, and the two states were
indistinguishable whenever they were the same row. Both marks live in a two
column gutter the band never paints over: >

       ▌ 󱙺 󰦖 fix the archive redraw          claude/opus   open, not focused
         󱙺 󰧞 sidebar perf                  claude/sonnet
      ▸  󱙺 󰀦 voice dictation                  codex/gpt   focused, not open
<
Their groups are `PaseoRowCaret` and `PaseoRowBar`, with one variant per band
(`PaseoRowBarHover`, `PaseoRowBarActive`) -- a foreground-only group on a
filled row is a hole in the middle of the fill.

A PUSH REPAINTS THE SURFACE. Both directories are fed by the daemon rather
than polled, and nothing used to ask the screen to draw them again: archiving
a session left its row up until the next `j`, and an agent that started
working did not change colour until you moved. The data was right and the
picture was a second-hand copy of it. One archive produces three `remove`
events from a live daemon, so the repaint is coalesced -- and it redraws the
session strip and the list, not the Changes panel, which shells out to
`git status` per repo and is not what changed.

None of that was true before. Selection lived on the CURSOR, which volt resets
to line 1 after every click; nothing was drawn to say where it was; and the
cursor was never put on a row in the first place. So Sessions had working
keymaps and read as a tab you could only click, and Workspaces had no keymaps
at all.

Focus is held BY ID, so a list that moves under you -- and these are push-fed,
so they do -- does not take it with it. A reorder leaves focus on the same
session; killing the row you are on leaves you on whatever took its place.

A list longer than the tab scrolls, with a scrollbar in the last column, and
the hint bar stays put: a list that scrolls its own instructions away does it
exactly when it has grown enough to need them.

These are bound only while that tab is showing, and whatever they displaced
is put back on the way out -- the six panels share one buffer, so a `<CR>`
left bound here would try to apply an agent setting from the Changes tab.

                                                          *paseo-chat-stop*
Stopping a turn ~

`<C-c>`, or |:Paseo-stop|. One `cancelAgent` -- the same thing the app's stop
button does and the same thing `paseo agent stop` does. Nothing local is torn
down, because nothing local is what is running: the agent lives on the daemon
and the cancellation comes back as a `turn_canceled` on the timeline, like any
other turn outcome.

Nothing running is a NO-OP, deliberately not an error. `<C-c>` is a key you
hit reflexively.

    NOTE: `:Paseo agent stop` is a different command and shuts down the
    SIDECAR PROCESS, not a turn.

The other interrupt is |paseo-permission-overlay|'s "decline and stop", which
only works while a permission request is waiting to be answered -- it cannot
stop a turn that is running freely, which is what this is for.

                                                          *paseo-dictation*
Dictation ~

`<C-t>` in the composer opens the microphone; `<C-t>` again closes it and puts
what you said in at the cursor; `<Esc>` throws the recording away.

One key for both halves, and not a hold-to-talk one, because Neovim delivers a
keypress and never a key RELEASE -- "while held" cannot be expressed.

                                                      *paseo-dictation-opening*
OPENING IT IS A STATE OF ITS OWN. Two round trips stand between the key and the
first sample: the sidecar has to be up, and then the daemon has to accept the
stream -- which on a cold daemon is where the speech models load, and is
seconds rather than milliseconds. So there is a spinner, a count and a way out,
and THE BOX WILL NOT TAKE KEYS until the microphone is open: >

     ⠙ opening the microphone ──────────────────────────  0:03   󱊷  cancel
     what does this function do   ⠙ typing is off until the microphone opens
<
Typing is off for the length of it because anything typed there is racing the
transcript about to land on top of it. The composer LEAVES INSERT MODE rather
than merely going read-only -- a buffer you are still inserting into with
'modifiable' off rejects every keystroke with its own |E21| -- and it comes
back to insert mode, at the column you left, the moment the microphone opens.

A second `<C-t>` during the wait is a change of mind: it gives up on the start
rather than opening a second microphone. `<Esc>` does the same.

                                                        *paseo-dictation-meter*
THEN THE BAR BECOMES A METER. While the microphone is open, the bar over the
composer is the recorder, and the waveform scrolls along it: >

     󰍬 listening  ▁▁▂▃▅▆▇█▇▅▃▂▁▁▂▄▆▇▇▅▃▁▁▂▃▅▆▇▆▄▂▁  0:04   Ctrl + t  stop
<
ONE METER, NOT TWO. There was a second copy of the same wave inside the box as
well, and two rows of blocks answering the same voice is the same information
twice in the same glance -- so the one you are not looking at went, and the
one that stayed took the width the other had. The box still speaks up while
the microphone is OPENING, because a box refusing your keystrokes has to say
so; it has nothing to add once the wave is running.

It is there because "it is not clear when I am speaking"
is the whole problem with dictation you cannot see -- a word missed by a muted
microphone and a word missed by a thinking daemon look identical when the only
feedback is text that has not arrived yet.

THE LEVEL IS MEASURED ABOUT THE SIGNAL'S OWN MEAN, and that one word is the
difference between a meter and a flat line. A microphone is not obliged to hand
you a waveform centred on zero: the default source on the machine this was
fixed on sits at a constant +5642, a sixth of full scale, with the sound riding
on top of it. RMS taken about ZERO therefore reports that bias and not the
sound -- an empty room read 0.1693 to 0.1776 across eleven seconds, four tenths
of a decibel of swing, against a gate of several -- and speech cannot rescue it
either, because energy adds in quadrature and an ordinary voice over that bias
moves the total by a third of a decibel. The same eleven seconds measured about
the mean swing 10.5 dB.

NOTHING IN THE SCALE IS CALIBRATED TO A MICROPHONE. A headset an inch from your
mouth and a laptop across the desk are fifty times apart on the same sentence,
so every number the scale needs is measured from the signal, and the only
constants are ratios and bounds: >

    floor    the 5th percentile of the last twenty seconds -- the room,
             whatever the room is
    gate     the room's own spread over that floor, clamped -- a study
             swings 10 dB on its own, while a clean line swings 2
    top      the loudest thing heard in the last five seconds
    bottom   the gate, opened downward once the top has cleared it
<
The adaptive TOP is what keeps a loud input off the ceiling and a quiet one off
the floor: how far speech sits over a room floor is a fact about the room, the
gain and how far away you are sitting, so any fixed full scale is reached on
every syllable by one microphone and never by the next. Following the loudest
recent reading makes the bar full when you are as loud as you have been, which
is the question it is actually being asked.

Checked against 82 combinations of gain, DC bias and noise character, and
against real recordings rescaled from x0.05 to x4: silence flat on every one,
speech proportional on every one.

THE GATE IS NOT THE BOTTOM OF THE BAR, and using it as both was the fourth way
this drew a flat line at a working microphone. The window is cleared each time
you press the key, so it holds only the seconds since: start talking straight
away and there is no silence in it anywhere. The floor is then measured from
your own quietest syllable and the median from your own voice, which puts a
gate a dozen decibels above the floor most of the way up your actual signal --
ordinary speech drew one glyph and the odd stressed vowel spiked. On a soft
voice it was worse: the loudest thing in a ten-second window reached 11.8 dB
against a gate of 12.0, so the row never moved at all.

So once the TOP has CLEARED the gate -- which a room never does, and that is
what keeps silence silent -- the range opens downward and puts mid-speech in
the middle of the bar. In proportion, never as a step: measured on a quiet
room the gate sits at 9.65 against a top of 9.69, and a step there strobes the
bar between empty and full twenty times a second.

THREE VERSIONS OF THIS WERE WRONG BEFORE THAT, and the first two failed the
same way, by drawing a flat line at a working microphone -- which is the one
answer it must never give. One crept its floor upward at a fixed rate, so the
floor climbed over the voice a few seconds into a sentence and the wave died
mid-word; the next gated on a fraction of that floor, which in a loud room is
a bar an ordinary voice cannot clear. Both were built on a number that was
measuring a DC offset, which is why neither could be fixed by tuning it.

A RECORDER THAT DIES SAYS SO, with whatever it printed on the way out -- a
microphone that is busy, or refused. That used to be silent: the indicator
stayed lit, no audio was ever sent, and the key appeared to have stopped
working.

NEOVIM CANNOT RECORD AUDIO, so this shells out. The first of these that is
installed is used: >

    arecord     ALSA; on essentially every Linux box with sound
    rec         sox
    ffmpeg      PulseAudio on Linux, avfoundation on macOS
<
`:checkhealth paseo` reports which one it found, or that it found none.
|paseo-config.voice| `recorder` overrides the search with a full argv, for a
machine with two sound cards or a device that has to be named -- it still has
to produce RAW PCM16 mono on stdout, headerless, because that is what goes
over the wire.

Audio is streamed WHILE YOU SPEAK rather than recorded and then uploaded: the
daemon transcribes as it goes, so by the time you stop talking most of the
work is done and the text arrives in about as long as it takes to lift your
finger.

CHUNKS ARE NUMBERED FROM ZERO, and that is not a detail. The daemon
acknowledges the stream itself with `ackSeq: -1` and reassembles the audio by
sequence, so a first chunk numbered 1 leaves a hole at 0 that never fills:
every chunk waits in the reorder buffer, nothing is transcribed, and
`dictation.finish` gives up with "Timed out waiting for final transcription".
Which is exactly what dictation from this editor did, on a daemon whose own
app dictates fine.

THE DAEMON DOES THE TRANSCRIBING. A microphone is not enough -- if it has no
speech model it says so, in its own words, the first time you press the key.
That is a Paseo setting, not one of this plugin's.

Speech-to-TEXT only. Paseo also has a duplex voice mode with synthesised
replies; an editor that talks back needs a player, an interrupt and somewhere
to put the transcript, which is a surface rather than a key.

                                                        *paseo-chat-composer*
The composer ~

It is an ORDINARY buffer, so your insert-mode keymaps, completion,
abbreviations and undo all work. That is the difference between writing a
prompt and filling in a text field, and it is why |:Paseo-ask| does not go
through `vim.ui.input`.

On the full-screen surface it GROWS with the prompt, between
|paseo-config.ui.float.composer_min| and |paseo-config.ui.float.composer|, and
shrinks back when you send: >

    ─ claude/sonnet-5 · acceptEdits · 58% left · ~/Code/kora ─ ⠹ 14s ─ 󰌑 send ─
     why is the ref suite opening a file it then deletes?
<
A box standing at its configured height over an empty buffer was the largest
and emptiest shape on the screen: seven rows of flat card colour with nothing
saying you could type in it. Resting at ONE row is the same mistake the other
way round -- that is the shape of `:e `, not of the place you write a
paragraph, and it is where every session starts. So the floor is three.

The ceiling is a SHARE OF THE SCREEN on the buffer surface rather than a flat
seven: that surface is the whole window, a fifty-row terminal has forty rows
of transcript on it and most of them are blank, and the box was still the
seven rows it gets in a float over your code. See |paseo-config.ui.buffer|.

Wrapped lines count towards the height -- `wrap` is on, so a 300-column
paragraph is four rows on screen, and asking the buffer for its line count
would say one and leave the cursor off the bottom.

THE TEXT ABOVE THE CURSOR STAYS ON SCREEN. The box is resized from
`TextChanged`, which fires AFTER Neovim has already scrolled: press `<CR>` in a
one-row box and line 1 goes above the top of the window to keep the cursor
visible, and only then does the box grow. Neovim never scrolls back -- it
scrolls as far as it must to keep the cursor visible, and the cursor already
is -- so the box grew and the line you had just typed stayed the only one you
could see, with everything above it still in the buffer, still in the send,
and invisible. Whenever the whole draft fits, the box is scrolled to the top
of it; past the ceiling it is a viewport onto something longer than itself and
Neovim's own behaviour is the right one.

                                                     *paseo-chat-keys-send*
NO BOX IS DRAWN AROUND IT under `plate`, which is the default and where nothing
else on the surface has an edge either. A hard rounded rule around the composer,
inside a window whose own edge is invisible, above cards with no frames, was
the one thing on the dashboard that ignored |paseo-config.ui.style|. What
separates the box from the transcript now is what separates every other card
from it: one tier of elevation, and a title row. Under `rounded` and `square`
it keeps a real frame, because that is what those styles are for.

The title row is |paseo-chat-header|, and it ends with HOW TO SEND. Both keys,
because they are not interchangeable: `<CR>` sends from normal mode and opens a
line from insert mode, so the one that works while you are still typing is
`<M-CR>` -- Alt and Enter. `<C-CR>` is bound beside it for terminals that speak
the kitty keyboard protocol; the ones that do not never deliver it.

`<C-s>` IS NOT EITHER OF THEM. It means THE SESSION LIST on the chrome, in
every terminal, and on the session strip drawn four rows above the box -- so a
composer that quietly sent on it was one key with two meanings, both advertised
on screen at once. From the composer it now does what it does everywhere else.

Its groups are `PaseoComposerBar` (the title row, and the base every cell on
it is combined with), `PaseoComposerBorder`, `PaseoComposerLabel`,
`PaseoComposerHint` and `PaseoComposerKey` -- separate from the card's, so
|paseo-config.ui.theme| can move the composer without moving every card. The
microphone meter adds `PaseoVoiceOn` for the recording dot and
`PaseoVoiceIdle` / `PaseoVoiceLive` / `PaseoVoiceLoud` for the wave.

The conversation is an ordinary buffer too, on purpose: `y`, `/` and soft-wrap
work on an agent's reply. Volt draws the chrome around it -- the tab bar, the
panels, the permission dialog -- because virtual text cannot be yanked.

                                                               *paseo-quit*
Quitting Neovim ~

Agent sessions belong to Paseo's background daemon. `VimLeavePre` stops only
the Neovim sidecar; it does NOT stop the daemon or its agents. A daemon started
by the plugin is started in the background for the same reason.

WHICH DAEMON IT IS DECIDES WHETHER YOU ARE ASKED. A daemon that was already
running when this Neovim connected -- the desktop app's, or one left behind by
an earlier session -- goes on running without us, so quitting risks nothing and
nothing is asked, however busy its agents are. The question is only worth
asking about the daemon this Neovim started itself.

Under `open = "here"` the buffer surface is the window you were in, so `:q`
there closes that window -- and if it was the last one, quitting Neovim is
exactly what you asked for and the warning below applies. Under `open = "tab"`
it has a tab page of its own, so `:q` on it closes that tab.

With |paseo-config.quit.warn_active_agents| enabled, normal whole-editor
routes (`:q`, `:qa`, `:wq`, `:x`, long forms, `ZZ`, and `ZQ`) warn when a
non-archived agent session is running, starting, queued, or waiting for
attention. Idle, failed, and closed sessions do not warn. The prompt offers
`Quit Neovim` and `Cancel` and explains that Paseo work continues. Closing a
split, Neovim tab page, or float does not warn; a forced `!` exit bypasses it.

Existing mappings and command-line abbreviations are not replaced. A central
quit router should call |paseo.quit.guard| around its own confirmation.

                                                          *paseo-colours*
Every colour is DERIVED from your colourscheme by default, and nothing here
depends on NvChad. Three keys control it, and they are different questions:

    |paseo-config.ui.colors|    where the eight base colours come from
    |paseo-config.ui.palette|   those eight colours, by name
    |paseo-config.ui.theme|     finished highlight groups

`palette` sets a TOKEN and `theme` sets a GROUP. Everything below still runs on
a token, so naming two colours gets a coherent set and the colour reaches every
group derived from it; a group override is the one group you named.

The rest of this section is what `colors = "auto"` does.

BACKGROUNDS are an elevation ladder stepped off `Normal`: the editor, the
surface two points away, a card five, a chip eight, the selected row eleven.
On a light background every step goes the other way. Depth comes from that
ladder rather than from drawn boxes, which is the idea behind the default
|paseo-config.ui.style| of `"plate"`.

ACCENTS get four stops each -- `PaseoGreen0` through `PaseoGreen3`, blended
towards the background -- so there is something to fade a flash through, shade
a heat scale with, and draw a divider in that is not content weight.

Where the accents come from is a chain, and the order matters. With NvChad,
volt's `Ex*` groups, which are base46's palette. Without it, `DiagnosticError`
/`Removed`, `DiagnosticOk`/`Added`, `Function`, `DiagnosticWarn`/`Changed` --
the groups that MEAN what we mean. `Added` before `String`, because on
`morning` `String` is magenta, so a tool that succeeded was drawn the colour
of a string literal.

Volt's `Ex*` groups are deliberately NOT read on the non-base46 path: volt's
own fallback writes `ExBlue = { fg = get_hl "Function" }`, and
`volt.utils.get_hl` returns a TABLE rather than a colour, so on every setup
without NvChad each accent resolves to `#000000`. Black is not obviously wrong
on a dark theme, which is why it went unnoticed. It is simply invisible.

Three corrections are then applied, each of which a real colourscheme forced:

  - An accent used as TEXT is pushed until it is legible on whatever it sits
    on. Both directions are tried and the better result wins; a colour that
    already clears the bar is left exactly alone.
  - DIM has to be dimmer than body text, and neutral with it. `morning` sets
    `Comment` to pure blue: quiet by luminance, loud by saturation.
  - A bar's TRACK is derived from the background, because a track is the
    absence of fill.

IDENTITY colours -- the dot beside a repo or a project -- are a separate set of
eight, not the semantic accents: four collided in a list of four, and red
already means "this failed". They are hue rotations off the theme's blue,
stepped by the golden angle so consecutive indices land far apart on the wheel.

On a TRANSPARENT theme -- `Normal` with no background -- no background is
painted at all. Selection is then signalled by removing dimming rather than by
adding a fill, which is better than an opaque rectangle over someone's
wallpaper.

Override any group with |paseo-config.ui.theme|. Setting the group yourself
after `setup` does NOT survive a colourscheme change, because the derivation
re-runs on |ColorScheme| and overwrites it.

                                                            *paseo-glyphs*
A Nerd Font is REQUIRED. Every glyph lives in one registry,
`lua/paseo/ui/icons.lua`, defined by CODEPOINT rather than by literal bytes.

The codepoints are the point. Twice the bytes of a Private Use Area glyph have
been lost out of a source file, and an empty icon is not a visible failure:
the line still draws, and "off" and "broken" look identical. The test suite
walks the whole registry and asserts every entry is at least one cell wide.

                                                        *paseo-chat-timeline*
The transcript shows what the agent is DOING, not only what it says: files
read, commands run, edits made, searches, sub-agents, and its reasoning.

Each is a card, collapsed to one line, with a status glyph -- `md-progress_`
`clock`, `md-check_circle`, `md-close_circle` and `md-cancel` from the
registry, named there rather than pasted here. See |paseo-glyphs|.

On the default |paseo-config.ui.style| a card has no frame: the status colour
is carried by a one-column accent bar down its left edge, the same shape a
message of your own gets. `"rounded"` puts the boxes back.
`<Tab>` expands one to show what it actually did -- a command's output and
exit code, an edit's diff, a read's line range, a search's matches, a
sub-agent's own log of the work it delegated, and for a tool nothing here has
a schema for -- an MCP tool, mostly -- its arguments by name and what it
answered. A failed call shows its error without being expanded.

A card is updated IN PLACE when the call finishes; it does not appear twice.
It is also MERGED rather than replaced. The live subscription is not the
projected timeline the app renders: a sub-agent's terminal event arrives in its
raw shape, knowing less than the thirty before it, so taking each event whole
made a finished card fall back from `Explore  <what it was asked>` to the bare
tool name the instant it succeeded. What a later event knows wins; what it has
forgotten does not.

By default a command is ALREADY EXPANDED while it runs, and folds to its one
line when it succeeds -- watching the output arrive is most of the reason to
have the window open, and a card that hides it until you press a key tells you
the agent is busy and nothing else. A failure stays open. `ui.expand` changes
this: `"always"`, `"never"`, or the default `"running"`. A card you have
toggled by hand is yours from then on and is never folded back under you.

                          *paseo-terminals* *paseo-chat-terminals*
Paseo runs TERMINALS as well as agents -- the `claude` or `codex` sessions you
started in the app are PTYs on the daemon -- and A TERMINAL IS A SESSION. It
lists on the Agents & terminals tab beside the agent sessions, and opening one shows it on the
CHAT TAB, where the conversation would be. |:Paseo-term| goes to that list.

It used to be a surface of its own: a rail of names, a title bar, the terminal
and a backdrop -- four windows over the top of whatever you were looking at,
with its own geometry, its own z-index and its own keymaps. That shape was
floaterm's, and it was the wrong one to borrow. A terminal you have to open a
second application to reach is not a session; it is a place you get stuck, and
the way back out was `q`.

Now there is one surface, and what changes is what fills the panel area: a
conversation and its composer for an agent, the PTY outright for a terminal.

                                                       *paseo-session-strip*
THE SESSION STRIP, under the tab bar, is what makes that legible. One chip per
session in this workspace, agents then terminals, the one you are in lit: >

    󱙺 main   󱙺 reviewer   󰆍 lazygit   󰆍 shell        Ctrl + s  sessions
<
It is on EVERY tab, because "which session am I in" does not
stop being worth answering when you look at Usage -- and a terminal has no
transcript and no composer, so without it the dashboard could be showing a PTY
with nothing on screen naming it. A chip is a click; `<C-s>` is the keyboard.

Exactly one row, always. It degrades the way the tab bar does -- names, then
glyphs, then a `+N` -- because volt records each section's row once and a
strip that grew by a chip on hover would draw past the end of the buffer.

In a terminal ~

    <C-s>     the Agents & terminals tab -- the way out
    <C-j>     the next session here, <C-k> the previous
    <M-1>..6  jump to a tab
    q         close the dashboard, from normal mode
<
AND A CHAT PICKED OUT OF THAT LIST OPENS THE CHAT. Which session the Chat tab
is on outlives a trip through the panels, so `<C-s>` out of a terminal and an
agent chosen from the list used to come back to the Chat tab still showing the
same PTY: the screen did not change, and the key read as broken. Opening a
chat moves the session pointer as well as the tab.

ALL OF THESE ARE BOUND IN TERMINAL MODE as well as normal, which is the only
way any of them is worth having: a key you must press `<C-\><C-n>` to reach
first is a key you do not reach. That does take them from whatever is running
inside -- right for `claude`, wrong for `tmux` -- so any of them can be set
`false` in |paseo-config.ui.terminal|.

The DIGITS are deliberately not bound: a bare `5` in a terminal costs you
`50k` to scroll back, and `<M-5>` reaches the same tab. `<C-c>` is not bound
either -- it is SIGINT, and belongs to the program.

`<Esc>` is never bound. It belongs to the PTY, so vim running inside one can
still leave insert mode, and `<C-\><C-n>` is Neovim's own way out.

On the Agents & terminals tab, `c` starts a terminal, `R` renames one and `d` kills it
(asked first -- something is usually running in there). See |paseo-chat-lists|.

                                                     *paseo-terminals-presets*
`c` opens a SCREEN, not a prompt -- the same card renderer every other choice
in this plugin uses, because it was a `vim.ui.select` of bare labels opened
over a surface that was itself an overlay. It offers a shell, then one entry
per provider the daemon has -- `claude` and `codex` today, and whatever you
enable in Paseo tomorrow, because the list is read from the daemon rather than
written here -- then anything in `ui.terminal.presets`, then a free-text
command: >

    ui = {
      terminal = {
        presets = { "lazygit", { label = "Top", command = "btop" } },
      },
    }
<
Nothing checks that a command exists, on purpose: the terminal runs on the
DAEMON's host, which is not necessarily this machine, so the honest failure is
the PTY printing `command not found`.

                                                      *paseo-terminals-names*
A name you give with `r` is kept HERE, by the plugin, and the daemon is told
as well. That is not belt and braces: `renameTerminal` sets a terminal's
`title`, and `title` is also what the PTY reports for itself -- so the shell
overwrites your name with `user@host:~/dir` within a second, and every
terminal in one directory ends up labelled identically. The list therefore
shows, in order: the name you gave, the stable one the daemon assigned
(`Terminal 3`), then the live title.

                                                     *paseo-terminals-render*
A terminal here is a REAL terminal. It is `nvim_open_term`, the same libvterm
behind `:terminal`, fed the PTY's own bytes -- so colour, the cursor, and a
TUI redrawing itself all work, and what you type goes back to the daemon.
Scrollback comes with you on attach, when the daemon supports it;
|:checkhealth| `paseo` says whether yours does.

A terminal DYING is a directory update that no longer lists it, never a
process exiting under us -- Paseo owns the process, not Neovim. The list drops
the row and the surface stays open, showing an empty pane, because closing
your terminal manager because a process ended is not what you asked for.

                                                       *paseo-chat-history*
The conversation is the agent's real timeline, fetched when the chat opens,
tool calls and all. Reopening it shows what was said and done before --
including from a previous Neovim session, because the agent lives on the
daemon and outlives the editor.

                                                       *paseo-chat-context*
Context is ATTACHED AND VISIBLE. |:Paseo-ask| on a hunk puts a line like >
    > attached: clm_api/app/main.py:42 (clm_api)
<in the composer, so you can see exactly what is about to be sent and delete
the line if you change your mind. Attached blocks are sent BEFORE your prose,
so the agent gets the location first and the question second. What is attached
is a reference, not the code -- see |paseo-ref|.

                                                       *paseo-chat-images*
Neovim's clipboard is TEXT. An image copied from a browser or a screenshot
tool never reaches a register, so an ordinary paste cannot see it. `p`, `P`
and `<C-v>` in the composer therefore look at the real clipboard first --
`wl-paste`, `xclip` or `pngpaste` -- read the bytes as binary, and carry them
to the daemon as base64 beside the prompt.

PASTE IS JUST PASTE. This used to be a key of its own, `<C-v>`, advertised in
the composer's winbar; a paste key you have to be taught is a worse answer
than `p` working, and the hint cost four columns of a narrow pane.

What lands in the BUFFER is a placeholder: >
    [Image #1] why is the right-hand panel empty here?
<The bytes are not in the text, which keeps the prompt something you can read
and edit, and the number is how a sentence refers to one of several images.
Deleting the placeholder does not detach the image -- clear the composer, or
send and start again.

With no image on the clipboard the key does its ORDINARY job -- `3p` is still
`3p` and `"ap` is still `"ap`, because the count and the register are carried
through. |:Paseo-image| takes a path instead, and works with no clipboard
reader installed at all.

Images larger than 10 MB are refused here rather than after a round trip; no
provider accepts one, and base64 makes it a third larger again.

                                                         *paseo-chat-agent*
One agent per directory, reused across questions. A fresh agent per question
throws away the context that makes the second question cheap. The provider
comes from |paseo-config.paseo.provider|, or from whatever the daemon reports
as ready.

11. PERMISSIONS                                            *paseo-permission*

When an agent asks to do something its mode does not cover, it BLOCKS until
the request is answered. The dialog shows the request and the exact thing
being approved -- the command, or the diff -- rendered as the same card the
transcript uses.

                                                    *paseo-permission-keys*
    1-9       choose that action
    y         the first "allow" action
    n         the first "deny" action
    N         deny and interrupt the turn
    <Esc>     dismiss WITHOUT answering; the request stays pending
    q         the same

`<Esc>` deliberately does not deny. Silently denying on a stray keypress
throws away whatever the agent was doing. The request stays pending, the
header shows `` needs you``, and `gp` in the conversation reopens it.

A pending request also stops the spinner (see |paseo-chat-header|): the agent
is not working, it is waiting for YOU, and a spinner there would blame it for
a delay that is yours.

The actions are the PROVIDER'S own -- "allow once" and "allow for this
session" are different answers, not the same one. A provider that offers none
gets a plain Allow/Deny pair.

Every request is also logged inline in the transcript, so it is part of the
conversation and answerable even after the dialog is dismissed.

A request answered in the Paseo desktop app closes the dialog here too. To
avoid being asked at all, set a more permissive mode with |:Paseo-mode|; to be
asked about everything, set `default`.

                                               *paseo-permission-questions*
When the agent asks YOU ~

A question -- Claude's `AskUserQuestion`, and the `ask_user` the other
providers wrap in the same envelope -- arrives as a permission request like
any other, and it is NOT the same act:

    A request to ACT      the provider's actions are the answer. Allowing it
                          is the whole reply.

    A QUESTION            the answer travels back inside the tool input.
                          Allowing it only consents to the ASKING. An allow
                          with no answers attached reaches the agent as "The
                          user did not answer the questions" -- approved, and
                          silent. Whichever button was pressed.

So the overlay answers a question rather than approving it, and `<CR>` there
sends your answers instead of a bare allow.

                                          *paseo-permission-question-keys*
    1-9       pick that option
    j k       move among the options, for the ones past the ninth
    <Space>   pick the one you are on
    <CR>, y   SEND, once nothing is missing -- until then, go to what is
    <Tab>     the next question · <S-Tab> the previous
    i, o      answer in your own words, in a box you can type in
    c         note WHY, about the answer you picked
    x         clear this question's answer (and its note)
    s         skip, where the question may be skipped
    n, N      decline to answer (N also stops the turn)
    <Esc>, q  later; the request stays pending, `gp` reopens it

ONE question at a time, and the card says which: `2 of 3`, with a dot per
question above it -- `●` answered, `◉` where you are, `○` not yet. A skipped
optional question stays `○`, because skipped and answered are different things
and should not look the same.

The answers are still sent as ONE response; the stepper is how they are
PRESENTED, and the counter is what says so. All of them at once was the
previous answer to the same problem, and it was the wrong one: four questions
stacked in a float is a wall you skim, and the number -- the one thing you
needed -- was still yours to count. `2 of 3` is that number, on every frame,
and the hint bar reads `next` until the last question and `send the answers`
on it.

`<CR>` sends only when nothing is missing. Until then it JUMPS to the first
question that is, rather than refusing with a message that does not say which
one: half a reply is not a smaller answer, it is a wrong one.

An option's DESCRIPTION is shown in full, wrapped under the option it belongs
to rather than truncated onto one row -- the half that fell off the end was
usually the half that told it apart from the option below. It is drawn for the
option you are ON and for every option you have PICKED, so an answer does not
lose its meaning the moment you choose it.

`c` writes a NOTE about the answer: the caveat the options did not cover, like
"the second one, but only for new workspaces". It never replaces the pick --
the label still travels in `answers`, and the remark rides beside it in
`annotations`, keyed the same way, so a reader that knows nothing about notes
still gets an option it recognises. The note also appears in the transcript
badge beside what was answered, because a caveat that exists only in the
request nobody can find later is not a record of anything.

A multi-select question ticks as many options as apply and stays put; a
single-select one replaces and moves on. The marker says which before you
press anything -- a checkbox where a second pick ADDS, a radio where it
REPLACES. Several answers to one question are sent as `", "`-joined labels,
quoting any label that contains the separator, because that is the one form
the provider parses back.

Typing an answer opens a REAL buffer inside the card, not a prompt: your
completion, abbreviations, insert-mode maps and undo all work, and `<CR>` in
insert mode is a newline. `<M-CR>`, or `<CR>` in normal mode, saves it;
`<Esc>` twice discards it. That is the composer's contract verbatim -- down to
NOT being `<C-s>`, which is the session list -- because it is the
same act. A question with no options at all opens the box for you and starts
insert -- there is nothing else to do on one.

There is no timeout, here or in the daemon. A question waits until it is
answered.

                                            *paseo-permission-question-card*
THE RECORD IT LEAVES FOLDS UP. The picker is transient and the conversation is
the record, so the question, its options and their descriptions are written
into the transcript as a card of their own. Answered, that card is ONE line --
the question's header and what you chose -- and |paseo-chat-keys| `<Tab>`
opens it again: >

      Input box  Floor of 3, cap scales with the surface
     The composer grows from 1 row up to a flat 7-row cap. What shape
     should the box take?
     󰗠 Floor of 3, cap scales with the surface
         Empty box is 3 rows so it reads as a field, not a one-liner.
     · Keep the 1-row floor, just fix the scroll
         Minimal change: the empty box stays a single row.
<
It used to be neither. It stood open for the rest of the session -- a dozen
lines of identical grey, every option run onto one line behind an em dash, for
a decision whose whole outcome fits in the badge -- and no key folded it,
because the card was built as not collapsible. The option you TOOK is now
ticked and the rest are not, each description sits under its own option, and
an UNANSWERED question still draws open whatever |paseo-config.ui.expand|
says, because the options are the thing being asked about.

A card is TEXT, NOT MARKDOWN. The transcript is `filetype=markdown` so that
what the agent writes reads the way it wrote it; an option description is not
that -- it is a string landing in the same buffer, where treesitter finds
emphasis in it and styles over our own highlights. No extmark priority undoes
that, because strikethrough and italic are attributes rather than colours. One
real description read "a share of the surface (~a third of the window) ... a
long prompt gets ~15 rows": two tildes in a paragraph is a GFM strikethrough,
and everything between them was drawn struck through, across four wrapped
lines, starting mid-sentence. So `**`, `~~` and backtick pairs come out of
card text and a lone `~` becomes the sign it meant. `_` is left alone --
stripping it turns `composer_min` into `composermin`, and a card lying about
an option's text is worse than one drawing it in italics.

                                              *paseo-permission-overlay*
Where it draws ~

Over the CHAT WINDOW, not over your editor. The conversation dims behind it
and the card is laid on top of the thing it is about, on either surface -- the
sidebar's split or the dashboard's pane -- because a question is about the
conversation and belongs in the conversation's space rather than over the file
you happened to be reading.

Too narrow or too short a chat window (under 48 columns or 14 rows), or no
chat window at all -- `gp` pressed from somewhere else -- and the SAME card
opens centred on the editor. Same keys, same layout; only where it sits
differs. See |paseo-config.ui.answer|.

While it is up it owns the keys, so the dashboard's `1`-`6` pick an option
rather than switching tab. Dismiss with <Esc> and they come back. Switching
surface with |paseo-chat-keys| `<C-f>` closes the chat window the overlay is
anchored to, so the overlay is reopened on the new one -- with your answers,
which are held on the chat rather than in the window.


                                                   *paseo-permission-plan*
When the agent has a plan ~

A finished plan -- Claude's `ExitPlanMode`, and whatever a provider maps onto
`kind == "plan"` -- arrives as a permission request like any other, and
approving one is TWO decisions, not one:

    BUILD IT?             yes, or keep planning.

    WITH HOW MUCH ROPE?   the mode the session runs in from here. The daemon
                          decides this itself if you do not: every approved
                          plan lands in `acceptEdits`, whether or not that is
                          what you wanted.

So the dialog offers one Implement per mode you could land in, least rope
first, and applies the mode after the approval. The list is filtered against
what the provider actually reports, so codex -- which has no `acceptEdits` --
is offered the modes it has rather than the ones Claude has.

                                              *paseo-permission-plan-keys*
    1         implement, and accept file edits
    2         implement, in auto mode
    3         implement, and keep asking about everything
    y         implement -- the same as `1`, the most cautious of them
    n         reject, and keep planning
    N         reject, and stop the turn
    j k       scroll the plan · <C-d> <C-u> by pages · gg G the ends
              -- and the mouse wheel, over the plan itself
    <Esc>, q  later; the request stays pending, `gp` reopens it

Paseo adds a fourth Implement when the session was in `bypassPermissions`
before it entered plan mode; that one restores it, and is the provider's own
button rather than one of these.

A plan is decided in the same overlay a question is answered in
(|paseo-permission-overlay|), and the plan itself is shown there as a REAL
buffer -- scrollable and searchable with `/`, with the buttons as chrome
around it. It has to be a real buffer: the card is drawn as virtual text,
virtual text cannot be scrolled, and the version before this therefore
budgeted the plan against the screen and truncated it -- so on a plan longer
than the terminal you were approving the part that happened to fit.

The body is FOCUSABLE, which is what makes the mouse wheel reach it: an
unfocusable float is one the mouse lands straight through, so the wheel
scrolled the conversation behind the plan while the plan sat still. It carries
the same keys the card does, so landing in it with the mouse is not a dead
end. The percentage and bar in the title say how far down it you are --
without one, a document that scrolls cannot be told from one that does not.

A plan takes the WHOLE width the conversation has, rather than the
|paseo-config.ui.answer| `width` cap a question's options are held to: a plan
is a document with code in it, and that cap wrapped every fenced block.

It has to be on screen at all because a plan request carries no tool `detail`
whatsoever -- the markdown travels in the tool input -- so there is nothing
else that says what you are agreeing to. The transcript records it too,
capped, so which plan you approved is still readable tomorrow.

12. AGENT SKILLS                                                *paseo-skills*

This plugin ships five agent skills in its own `.agents/skills/`:

    workspace           finding your way around a multi-repo workspace
    workspace-commit    one conventional commit per repo, across a workspace
    workspace-pr        one pull request per member repo, cross-linked
    explain-change      the rubric |:Paseo-explain| uses
    paseo-sdk           writing a program against the Paseo daemon

They are plain markdown over plain git and `<project>/.ws/workspace.toml`.
Nothing in them needs a binary this plugin does not ship, which is what makes
them usable by whatever agent you happen to be running.

                                                          *paseo-skills-where*
Where they go ~

An agent only discovers skills near its working directory, so bundled ones are
invisible everywhere except inside this repository -- which is exactly
backwards, because three of them describe multi-repo workspaces and those live
somewhere else. |:Paseo-skills| `install` fixes that.

GLOBAL IS THE DEFAULT, and it is not a matter of taste. An agent working in a
workspace has a working directory of `<project>/.workspaces/<name>/<repo>` --
a MEMBER worktree. It reads project skills from there and from the repository
around it, so `<project>/.claude/skills` is two levels up and in a different
tree: invisible to the one agent these are for. `~/.claude/skills` is the only
target visible from inside a member, and it is also right on the merits, since
these describe a workflow rather than a project.

`install project` exists for the case where the agent really does run at the
project root. It refuses when that root is itself a git repository, because
adding files to your repo uninvited is not a thing a plugin does.

                                                           *paseo-skills-link*
Links, or copies ~

A symlink by default: this plugin stays the source of truth, so updating it
updates the skills with no second step. |paseo-config.skills.method| `= "copy"`
is the alternative, and is the default on Windows.

Removing and reinstalling the plugin leaves a link pointing at nothing.
`install` repairs that WITHOUT `force` -- a link to nothing is nobody's data,
and needing `force` to recover from the ordinary case would make it feel
dangerous.

                                                         *paseo-skills-safety*
What it refuses ~

    already installed      skipped, and said so
    a link pointing at nothing      repaired, no `force` needed
    a link pointing somewhere else  refused; `force` replaces it
    a directory paseo did not create   refused; `force` MOVES it to
                                       `<name>.paseo-backup` and names the path

`force` never deletes anything you have. It moves a real directory aside; it
replaces a symlink, because a symlink is a pointer rather than data. `dry`
prints the same plan without touching the disk.

Nothing here ever happens on its own. Writing into `~/.claude/skills` changes
the behaviour of a DIFFERENT program, and no Neovim plugin gets to do that as
a side effect of a command about worktrees. The most you will see is one line
after assembling a workspace, once per session, naming the command.
