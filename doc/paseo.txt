1. INTRODUCTION                                           *paseo-introduction*

paseo.nvim makes reviewing your own diff the path of least resistance, and
hands the confusing parts to an agent without leaving Neovim.

It is built around a `workspace`: one named unit of work spanning N git
worktrees, plus the untracked context they need. A worktree is per-repo; a
workspace is not, which is what lets a single unit of work span several repos
under a parent directory that is not itself a git repository.

Agents run on Paseo <https://github.com/getpaseo/paseo>, which abstracts
claude / codex / opencode.

==============================================================================
2. REQUIREMENTS                                           *paseo-requirements*

Hard:
  - Neovim 0.10+
  - `git`
  - gitsigns.nvim, telescope.nvim

Optional, for the Paseo backend:
  - the `paseo` daemon, running
  - `bun`, or node >= 22, for the sidecar

Run `:checkhealth paseo` to see what is present. Missing optional pieces
degrade the plugin to the `local` backend; they do not break it.

==============================================================================
3. SETUP                                                         *paseo-setup*

>lua
    require("paseo").setup {}
<
`setup()` is required. It merges configuration, registers |:Paseo|, and
installs a DirChanged hook that drops the resolved-repo cache.

==============================================================================
4. CONFIGURATION                                         *paseo-configuration*

Defaults: >lua
    require("paseo").setup {
      backend = "paseo",

      paseo = {
        -- url and home are absent by default: absent means "discover it".
        cli = "paseo",
      },

      workspaces = {
        dir = ".workspaces",
      },

      review = {
        context = 0,
      },
    }
<
                                                        *paseo-config.backend*
backend                                            string, default `"paseo"`

    `"paseo"` runs agents through the Paseo daemon. `"local"` runs them in a
    floaterm terminal and pastes prompts with `nvim_chan_send`. Paseo is the
    default and gets every feature.

                                                      *paseo-config.paseo.url*
paseo.url                                                 string, unset

    Daemon WebSocket endpoint, e.g. `"ws://127.0.0.1:6767/ws"`. Leave it unset
    and the endpoint is discovered; setting it pins the endpoint and skips
    discovery. See |paseo-daemon-discovery|.

                                                     *paseo-config.paseo.home*
paseo.home                                                string, unset

    Overrides `$PASEO_HOME`, which itself defaults to `~/.paseo`. Only affects
    where `config.json` is read from during discovery.

                                                 *paseo-config.paseo.provider*
paseo.provider                                            string, unset

    `provider/model` for agents this plugin creates, e.g.
    `"claude/claude-sonnet-5"`. Unset means "ask the daemon what is ready",
    which is the only answer that survives moving to another host.

                                                 *paseo-config.paseo.password*
paseo.password                                            string, unset

    Daemon password, if it has one. A local daemon does not.

                                                              *paseo-no-cli*
The `paseo` CLI is never invoked ~

    Not because it is broken -- `/usr/bin/paseo` is a wrapper that runs the
    Electron binary with `ELECTRON_RUN_AS_NODE=1`, so it is headless, prints
    clean output and its `--json` is parseable. It simply still pays Node
    startup: roughly 1 second against 8ms for the socket. Everything goes over
    `ws://…/ws` through |paseo-bridge| instead, with `GET /api/status` as a
    liveness probe.

    Two executables exist and only one is the CLI:

      /usr/bin/paseo      -> resources/bin/paseo, the CLI. Headless.
      /opt/Paseo/Paseo    -> the desktop app. Opens a window.

    A stale symlink from a CLI-only install can leave the desktop binary
    shadowing the CLI on `$PATH`, which looks exactly like the CLI being
    broken: a window appears and `--json` returns startup logs instead of
    JSON. `:checkhealth paseo` reports which one you have.

                                                     *paseo-daemon-discovery*
Daemon discovery ~

    6767 is the daemon's default port, not a constant, so it is resolved
    rather than assumed. Candidates are tried in order and the first that
    answers wins:

      1. `paseo.url` from |paseo-setup|
      2. `$PASEO_ENDPOINT`
      3. `daemon.listen` in `$PASEO_HOME/config.json` -- the daemon's own
         answer
      4. `127.0.0.1:6767`

    Each is probed with `GET /api/status`. A `401` counts as REACHABLE: the
    daemon is there and wants a password. Treating it as a miss is how you
    end up reporting "no daemon" about a daemon that is running.

    Only TCP listens can be reached. A `unix:` or `pipe:` listen is a
    different transport and is skipped rather than turned into a URL that
    cannot connect.

    `:checkhealth paseo` prints every candidate and what it answered.

                                                 *paseo-config.workspaces.dir*
workspaces.dir                              string, default `".workspaces"`

    Where assembled worktrees live, relative to a project root. Changing this
    is the single knob that moves them out of the project tree. See
    |paseo-workspaces|.

                                                 *paseo-config.review.context*
review.context                                          integer, default `0`

    Context lines asked of `git diff` when building the hunk quickfix list.
    Keep it at 0: a hunk header's line numbers only delimit the hunk itself at
    `-U0`, and a delete hunk's quickfix entry has to land on exactly the line
    `gitsigns.stage_hunk()` acts on.

==============================================================================
5. COMMANDS                                                   *paseo-commands*

                                                                      *:Paseo*
:Paseo [subcommand]

    Without an argument, equivalent to `:Paseo repos`.

:Paseo changes                                              *:Paseo-changes*

    Changed-files picker across every repo in the unit of work. The previewer
    shows `git diff HEAD` -- staged and unstaged together -- not the file.
    `<CR>` opens the file on its FIRST HUNK; `<C-q>` expands the selection
    into a hunk quickfix list; `<C-a>` expands everything.

:Paseo hunks                                                  *:Paseo-hunks*

    Every hunk in the unit of work as a quickfix list, one entry per hunk.

:Paseo stage                                                  *:Paseo-stage*

    Stage the hunk the quickfix list is on, then advance to the next.

:Paseo review [unified]                                      *:Paseo-review*

    A `:Gitsigns diff` panel per repo, each in its own tab, `tcd`'d to that
    repo. `unified` starts in the unified layout, which shows deleted lines
    inline.

:Paseo chat                                                  *:Paseo-chat*

    Open, or close, the chat for this directory. See |paseo-chat|.

:Paseo model                                                *:Paseo-model*

    Choose the provider/model new agents are created with, from what the
    daemon reports as ready. There is no hardcoded list: installed providers
    and configured models differ between hosts.

:Paseo qfask                                                *:Paseo-qfask*

    Attach every hunk in the quickfix list at once -- "explain this review"
    rather than "explain this hunk".

:Paseo ws [init|create|rm|ls|status]                           *:Paseo-ws*

    Workspace assembly. `init` opens the generated manifest for you to read
    before you `:w` it -- the comments in it are what init could not decide
    for you. `create <name> [repo,repo]` assembles worktrees; `rm <name>
    [force]` dismantles one and refuses if there is unsaved work.

:Paseo explain [kind]                                      *:Paseo-explain*

    Explain the change under the cursor. `kind` is `hunk` (default, falling
    back to `cursor`), `visual`, `cursor` or `file`. The reply streams into a
    split rather than an agent terminal -- switching to a terminal to read it
    is the context switch that breaks the review loop.

:Paseo ask [kind]                                              *:Paseo-ask*

    The same, with your own question instead of the rubric.

:Paseo agent [stop]                                          *:Paseo-agent*

    Sidecar and agent status. `stop` shuts the sidecar down; it restarts on the
    next request.

:Paseo repos                                                  *:Paseo-repos*

    List the repos in the current unit of work: the member worktrees of the
    containing workspace, or the single repo containing the cwd.

:Paseo health                                                *:Paseo-health*

    Shorthand for `:checkhealth paseo`.

==============================================================================
6. LUA API                                                         *paseo-api*

                                                            *paseo.repos.list*
require("paseo.repos").list({opts})                       -> |paseo.Repo|[]

    Every repo in the unit of work containing `opts.path` (default: the cwd).
    ALWAYS a list, even at length one — every caller iterates it, so widening
    a workspace from one member to six changes this function and nothing else.
    Possibly empty; never nil.

                                                         *paseo.repos.resolve*
require("paseo.repos").resolve({path})             -> |paseo.Repo| or nil

    The repository containing `path`, or nil. Results are cached per directory.

                                                         *paseo.repos.current*
require("paseo.repos").current({bufnr})            -> |paseo.Repo| or nil

    The repository owning a buffer.

                                                        *paseo.repos.relative*
require("paseo.repos").relative({repo}, {path})               -> string

    `path` relative to `repo.worktree`, or unchanged if it lies outside it.

                                                      *paseo.repos.invalidate*
require("paseo.repos").invalidate()

    Drop the resolved-path cache. Called automatically on `DirChanged`; call it
    by hand after creating or removing a worktree under the current tree.

                                                                  *paseo.Repo*
A repo is: >lua
    {
      name     = "clm_api",                     -- which repo this is
      worktree = "/home/you/Code/openfin/clm_api",
      gitdir   = "/home/you/Code/openfin/clm_api/.git",
    }
<
`name` comes from the common git dir, not the worktree's basename. A linked
worktree is named after the workspace ("otp-rate-limit"); what a picker row
needs to say is which repo it is.

`gitdir`, conversely, is `<repo>/.git/worktrees/<name>` for a linked worktree
rather than the common dir. That is also deliberate: it is per-worktree, which
is what identifies the member.

==============================================================================
7. WORKSPACES                                               *paseo-workspaces*

A workspace is a directory: >
    <project>/<workspaces.dir>/<name>/
<
Membership is detected from the filesystem, not from a registry. Either that
directory is itself a git worktree — a single-repo project — or its immediate
children are, one per member repo. Nothing has to have created it for
detection to work.

==============================================================================
8. GIT                                                             *paseo-git*

`paseo.git` is the only module that shells out to git. Two notes matter to
anyone reading hunks out of it.

                                                             *paseo-git-hunks*
require("paseo.git").hunks({repo}, {changes})            -> |paseo.Hunk|[]

    Every hunk, as quickfix-ready positions. A hunk's `lnum` is the line
    `gitsigns.stage_hunk()` acts on. For a deletion, `@@ -a,b +c,0 @@` gives
    `c` -- NOT `c + 1` -- because stage_hunk() acts on `added.start`, and for
    a pure deletion that is the line ABOVE the removed block. A deletion at
    the top of a file yields `c = 0` and clamps to 1.

    Untracked files never reach `git diff`; each becomes one synthetic
    `kind = "new"` entry.

                                                             *paseo-git-stage*
require("paseo.git").stage({hunk}, {callback})

    Stages one hunk, routing around the case gitsigns structurally cannot do.

    A WHOLE-FILE DELETION (`hunk.file_deleted`) has no file on disk, so no
    buffer can open on it and gitsigns can never attach -- staging through the
    hunk UI silently does nothing. Those, and untracked files, go through
    `git add` instead, which records a removal correctly. Everything else goes
    to `gitsigns.stage_hunk()`.

9. THE AGENT BRIDGE                                             *paseo-bridge*

Agents are reached through a sidecar: `bin/paseo-bridge.ts`, one Bun (or Node
>= 22) process per Neovim session, holding one WebSocket to the daemon and
speaking newline-delimited JSON over stdio.

It is not the `paseo` CLI because that boots Electron per invocation and costs
about 2.4 seconds. It is not a raw WebSocket in Lua because the frame codec is
the easy part: the real surface is subscriptions with server-issued IDs,
snapshot-then-update ordering, timeline epochs and cursors, `replacement`
invalidation and `subscription_restored` after reconnect.

                                                          *paseo-bridge-agent*
One agent per repository, reused. It is found again by the label
`paseo.nvim = review`, which is namespaced because several tools may manage
agents on one daemon. The provider is discovered from the daemon unless
|paseo-config.paseo.provider| names one -- installed providers and configured
models differ between hosts, so a hardcoded model id fails at creation.

                                                       *paseo-bridge-lifetime*
The sidecar starts on the first request that needs it and is stopped on
`VimLeavePre`. Agents it created keep running on the daemon and stay visible in
Paseo; closing Neovim does not archive them.

                                                         *paseo-bridge-local*
With `backend = "local"` there is no sidecar: prompts go to a floaterm terminal
through `nvim_chan_send`, wrapped in bracketed paste so a multi-line prompt
arrives as one block rather than being submitted line by line. No streaming,
no session reuse. It exists so a sidecar that cannot start is a degradation
rather than an outage.

10. THE CHAT WINDOW                                              *paseo-chat*

Two buffers in a split: the conversation above, the composer below.

                                                          *paseo-chat-keys*
In the composer ~

    <CR>      (normal mode) send
    <C-s>     send, from normal or insert mode
    q         close the chat

The composer is an ORDINARY buffer, so your insert-mode keymaps, completion,
abbreviations and undo all work. That is the difference between writing a
prompt and filling in a text field, and it is why |:Paseo-ask| does not go
through `vim.ui.input`.

                                                       *paseo-chat-history*
The conversation is the agent's real timeline, fetched when the chat opens.
Reopening it shows what was said before -- including from a previous Neovim
session, because the agent lives on the daemon and outlives the editor.

                                                       *paseo-chat-context*
Context is ATTACHED AND VISIBLE. |:Paseo-ask| on a hunk puts a line like >
    > attached: clm_api/app/main.py:42 (clm_api)
<in the composer, so you can see exactly what is about to be sent and delete
the line if you change your mind. Attached blocks are sent BEFORE your prose,
so the agent reads the code first and the question second.

                                                         *paseo-chat-agent*
One agent per directory, reused across questions. A fresh agent per question
throws away the context that makes the second question cheap. The provider
comes from |paseo-config.paseo.provider|, or from whatever the daemon reports
as ready.
