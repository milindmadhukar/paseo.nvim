1. INTRODUCTION                                           *paseo-introduction*

Paseo (https://paseo.sh) runs coding agents -- Claude Code, Codex and others
-- in a local daemon, and its desktop app is one way to drive them. This
plugin is another: every agent is a buffer, every pane a real split, and the
keys are Vim's.

The plugin talks to the daemon through a small sidecar process (Bun, or Node
22+) over one WebSocket. It never shells out to the `paseo` CLI.

Terms, as Paseo uses them:

    Project     a codebase the daemon knows
    Workspace   a directory in a project that agents work in: the checkout
                itself ("Local"), a git worktree, or several worktrees
                assembled side by side (|paseo-ws|)
    Agent       one conversation with one provider, in one workspace
    Subagent    an agent another agent started

==============================================================================
2. REQUIREMENTS                                           *paseo-requirements*

  - Neovim 0.11+
  - `git`
  - the Paseo daemon (the desktop app starts one), and `bun` or `node` 22+
  - a Nerd Font

Optional:
  - `wl-paste` (Wayland), `xclip` (X11) or `pngpaste` (macOS), to paste a
    screenshot straight off the clipboard (|paseo-images|)
  - `arecord`, `rec` (sox) or `ffmpeg`, for dictation (|paseo-dictation|)
  - `gh`, for pull-request status on the rail (|paseo-config.ui.pr|)
  - telescope.nvim, for |:Paseo-search| with a fuzzy sorter and a preview

No build step and no UI library: every surface is plain buffers and windows.

==============================================================================
3. SETUP                                                         *paseo-setup*

With lazy.nvim: >lua
    {
      "milindmadhukar/paseo.nvim",
      event = "VeryLazy",
      opts = {},
    }
<
`opts` is passed to `require("paseo").setup()`; see |paseo-configuration|.
(`VeryLazy` rather than `cmd = "Paseo"`, so `:checkhealth paseo` finds the
plugin before its first command.)

The plugin maps NO global keys. Bind the commands (|paseo-commands|), the Lua
functions (|paseo-api|) or the `<Plug>` names (|paseo-plug|) you want: >lua
    vim.keymap.set({ "n", "t" }, "<C-\\>", "<Plug>(paseo-native)")
    vim.keymap.set("n", "<leader>an", "<cmd>Paseo new<cr>")
    vim.keymap.set("n", "<leader>ak", "<cmd>Paseo ask<cr>")
    vim.keymap.set("v", "<leader>ak", "<cmd>Paseo ask visual<cr>")
    vim.keymap.set("n", "<leader>aw", "<cmd>Paseo workspaces<cr>")
<
`:checkhealth paseo` checks the daemon, the sidecar runtime, the clipboard
readers and the microphone.

4. COMMANDS                                         *paseo-commands* *:Paseo*

:Paseo                  Open or close the chat for this directory, on the
                        surface |paseo-config.ui.surface| names. With no
                        agent here yet it opens the new-task screen.

                                                                *:Paseo-new*
:Paseo new [worktree|agent]
                        A new session: Local (the project's own directory)
                        or in a new worktree. See |paseo-new|. `worktree`
                        opens the screen with "New worktree" chosen. `agent`
                        is a new agent in the session on screen instead.

                                                                *:Paseo-ask*
:Paseo ask [kind]       Ask an agent about code. The code becomes a chip
                        in the composer of the chat beside it, and you
                        write the question there (|paseo-ask-chips|).
                        {kind}:
                          `hunk`    the git hunk under the cursor: the
                                    buffer, unsaved edits included, against
                                    `HEAD` (so a staged hunk counts)
                          `visual`  the selection (use from visual mode)
                          `file`    the whole file
                          `cursor`  the line under the cursor
                          `qf`      every entry in the quickfix list
                        Without {kind}: the hunk, else the cursor line.

                                                            *:Paseo-explain*
:Paseo explain [kind]   Like `ask`, with the question already written and
                        sent: the bundled explain-change rubric. The same
                        {kind}s, except `qf`.

                                                         *:Paseo-workspaces*
:Paseo workspaces [all] The workspaces in this project, in a chooser
                        (|paseo-workspaces-keys|). `all`: every project's.

                                                             *:Paseo-agents*
:Paseo agents           The agents in the workspace containing the current
                        directory, in a chooser (|paseo-agents-keys|).

                                                             *:Paseo-search*
:Paseo search           Search every workspace, live agent, prompt you
                        sent, and archived chat in one picker, with a
                        preview of the chat (|paseo-search|). No default
                        key: map it globally (`<Plug>(paseo-search)`).

                                                           *:Paseo-settings*
:Paseo settings [group] The chat agent's settings card: permission mode,
                        thinking level, model and features (Fast, Plan, ...).
                        `mode`, `thinking` and `model` open that list
                        straight in your picker (|paseo-pick|); `features`
                        opens the card on the toggles. On a new-session
                        draft the three pick the draft's own choice.
                        See |paseo-settings|.

                                                               *:Paseo-stop*
:Paseo stop             Interrupt the turn the chat's agent is running.
                        `<C-c>` in the chat does the same.

                                                                 *:Paseo-ws*
:Paseo ws {sub}         The multi-repo workspace manifest (|paseo-ws|):
                          `init [raw] [dir]`  write a manifest, on a screen
                                              (`raw`: as a TOML buffer)
                          `edit [dir]`        open `workspace.toml`
                          `create {name} [repo,repo]`
                                              assemble a workspace
                          `rm {name} [force]` remove one
                          `ls`                list this project's
                          `status`            each one's repos and branches

Everything else is a key inside the chat or a Lua function (|paseo-api|).

==============================================================================
5. THE CHAT                                                       *paseo-chat*

Two surfaces show the same chats, and |paseo-config.ui.surface| says which
one |:Paseo| opens.

                                                                *paseo-native*
                                                                  *paseo-full*
Full screen ("native", the default) ~
ONE tab page, the Paseo tab, with every agent and terminal a listed buffer in
it: the workspace rail on the left (|paseo-rail|), the conversation over the
composer in the middle, and a panel on the right when you ask for one
(|paseo-panel|). `:bnext`, `:b {name}` and any buffer key move between agents
on the middle window. |:Paseo| (or `<Plug>(paseo-native)`) goes back to your
code and back again; `q` takes the tab down, and the agents live on.

                                                          *paseo-chat-sidebar*
Sidebar ~
The chat in a split beside your code (|paseo-config.ui.sidebar|). It is
where |:Paseo-ask| and |:Paseo-explain| put the chat, so the code you asked
about stays on screen (|paseo-config.review.surface|). `<C-f>` moves the
chat between it and full screen, both ways: from the Paseo tab it comes back
beside the code on the tab you came from, and the other agents open there
stay where they are. There is one sidebar per tab. Open it yourself with
`require("paseo.ui.chat").surface("sidebar")`.

                                                             *paseo-chat-keys*
In the composer ~
The box you type in is an ordinary buffer: your insert-mode mappings,
completion and undo all work, and it grows with what you write.

    <CR>        (normal) send
    <M-CR>      send, from normal or insert mode (<C-CR> where the
                terminal can send it)
    g<CR>       send the other way while a turn runs: queue it when
                sending steers, send now when it queues (<S-CR> too).
                See |paseo-send-behavior|
    <Up>        in an empty box: your previous prompts; <Down> back
    p  P  <C-v> paste -- an image if the clipboard has one (|paseo-images|)
    <C-t>       dictate (|paseo-dictation|)
    <C-c>       stop the turn (normal or insert)
    f           fork the conversation (|paseo-fork|)
    <C-s>       into the rail, on this agent
    <C-f>       between the sidebar and full screen
    q           close the chat

In the conversation ~

    <Tab> <CR>  expand or collapse the tool call under the cursor
    gp          reopen a pending permission request
    gs          this agent's subagents (|paseo-subagents|)
    f           fork the conversation
    <C-c>       stop the turn
    q           close the chat; on a subagent's view, back to its parent

On the full screen, from any of its buffers (|paseo-config.ui.native|):

    <C-b>       show or hide the rail, the cursor with it
    <C-h>       into the rail; in it, nowhere (it is the leftmost split)
    <C-s>       into the rail, on the agent on screen
    <C-p>       the panel: Settings, Changes, Usage
    <C-n>       a new session (|paseo-new|)

Every one of these can be moved or unbound: |paseo-config.keys|.

                                                        *paseo-send-behavior*
Sending while the agent works ~
By default a message sent mid-turn STEERS: it joins the running turn, as in
the Paseo app. |paseo-config.ui.send_behavior| `"interrupt"` stops the turn
and starts a new one; `"queue"` holds messages and sends them, as one, when
the turn ends. `g<CR>` does the opposite of the setting. The bar under the
conversation says what sending will do, and counts what is queued.

                                                                *paseo-images*
                                                           *paseo-chat-images*
Images ~
Copy a screenshot and press `p` in the composer (or `<C-v>` in insert mode).
The picture is read straight off the system clipboard with `wl-paste`,
`xclip` or `pngpaste`, because Neovim's registers only hold text. With no
image on the clipboard the key pastes text as usual, count and register
included.

Pasting a FILE works too: drag an image onto the terminal, or copy one in a
file manager and paste with your terminal's paste key. The terminal sends its
path (or `file://` URL), and a paste that is nothing but image paths is
attached instead of typed. Several at once are fine.

An attached image shows as a placeholder you can refer to: >
    [Image #1] why is the right-hand panel empty here?
<
The placeholder IS the attachment: delete it and the image is not sent. The
ones left are renumbered to the order they are sent in.
From a code buffer, `require("paseo").paste_image()` attaches the clipboard's
image to the chat, and `paste_image("~/shot.png")` a file.

Your terminal's own paste key (Ctrl+Shift+V) on a SCREENSHOT sends Neovim
nothing at all, so that one cannot be caught: use `p` or `<C-v>`.

                                                            *paseo-dictation*
Dictation ~
`<C-t>` in the composer starts recording; `<C-t>` again stops and puts the
transcript at the cursor; `<Esc>` throws it away. The daemon transcribes.
See |paseo-config.voice|.

                                                                  *paseo-fork*
Forking ~
`f` in the chat (or on an agent in the rail) forks the whole conversation.
A chooser asks where: a new agent beside this one, sharing its files, or a
new workspace of its own. Changing a running agent's model from the settings
card offers the same two forks.

                                                              *paseo-settings*
                                                         *paseo-chat-settings*
Settings ~
|:Paseo-settings| opens the agent's settings as cards in a float; on the full
screen they are also the Settings panel (`<C-p>`, then `1`).

Permission mode, thinking and model are each one row showing what is set.
Their letter, or `<CR>` on the row, opens the list in your picker
(|paseo-pick|): type to filter, `<CR>` to pick. Features stay checkboxes.

    h j k l     move between settings
    <CR>        open the picker / toggle the feature under focus
    m t s       pick the Mode, Thinking level or model (s)
    f           jump to Features
    r           re-fetch from the daemon
    q <Esc>     close

Fast and Plan are toggles among the features. From Lua,
`require("paseo").toggle_feature()` flips Fast (or the feature id you name)
and `require("paseo").toggle_plan()` flips Plan -- a Codex feature, or a
Claude mode.

                                                                 *paseo-panel*
                                                            *paseo-chat-usage*
The panel ~
The right-hand split on the full screen (`<C-p>`):

    1 2 3       Settings, Changes, Usage
    <C-p> q     close it
    r           reload

Changes lists the files the agent's workspace has changed (`<CR>` opens one
on the tab you came from). Usage shows the context window, the last turn's
cost, and the account's plan limits.

                                                                  *paseo-rail*
                                            *paseo-rail-sessions* *paseo-tree*
The workspace rail ~
The split down the left of the full screen: this project's workspaces, each
with its agents, subagents and terminals nested under it, the way the Paseo
app's sidebar lays them out. One status character leads each row: >
    ⠋   working          !   waiting on you
    ✗   failed           •   finished (bright: while you were elsewhere)
    $   a terminal
<
A workspace's row ends with its lines changed (`+120 -7`), and one with a pull
request has a line under it with its checks and review state.

Every real line is a row, so `j` `k`, counts, `gg` `G` and `/` work as usual.
The keys follow nvim-tree's (`g?` lists them):

    <CR> o      open the session; on a workspace, fold or unfold it
    l           unfold, step in, or open
    h <BS>      fold, or go to the parent
    <Tab> za    fold or unfold
    O           open the workspace: its newest agent
    P           the parent
    < >  K J    previous / next sibling; first / last sibling
    W E         fold / unfold everything
    a           a new session in this project (Local or a new worktree)
    A           a new agent in this row's session
    w           a new session in a new worktree
    t c         a new terminal in this row's session
    f           fork the agent
    y           copy the agent's ID
    R           rename the terminal
    d           archive the agent / kill the terminal (asks first)
    m           pin or unpin the workspace
    r           re-fetch
    .           everything you can do to this row, in a chooser (also a
                right-click)
    g?          these keys
    q <Esc>     back to where you were (`<C-w>l` too: it is a split)
    <C-h>       nothing: the rail is leftmost, so `<C-w>h` stays put

                                                                   *paseo-new*
Starting something ~
There are two things to start, as in the app:

    A new SESSION      a workspace of its own: the sidebar's `+`.
                       `<C-n>`, `a` and `w` on the rail, `<Plug>(paseo-new)`,
                       |:Paseo-new|.
    A new AGENT in     one more agent in a session that exists: the `+` on
    a session          its row of tabs. `A` and `t` on the rail,
                       `<Plug>(paseo-new-agent)`, `:Paseo new agent`, `n` in
                       the agent chooser.

A session's Where is "Local" -- the project's own directory, beside the
sessions already there -- or "New worktree". Local is the PROJECT's
directory, not the directory of the session you are looking at: from a
worktree it is the checkout that worktree was cut from, from inside an
assembled multi-repo workspace it is the project that holds them, and a
plain directory is its own project.

An agent goes into the session you pointed at, never one found by
directory: the row under the cursor on the rail, or the agent on screen on
the Paseo tab. Asked for with no session to go into -- the rail's project
line, or from your code -- it is a new session instead, and says so.

Both open the same screen: the composer you are about to write in, with the
choices drawn above it. For a session: >
    Start        a    Chat  Terminal        Where  w    Local  New worktree
    Base branch  b    main  dev  feat/x  …
    Provider p · Model s · Permission mode m · Thinking t · Features f
    ▌ your first message
<
An agent in a session has no Where row; the line under the choices names
the session it goes into.

Write the first message and send it: that creates the session (or the
agent), with that message as its first prompt. A terminal needs no message:
`<Tab>` up to the choices and `<CR>` on what to run.

In the choices: `h` `j` `k` `l` move, `<CR>` applies, a card's letter jumps
to it, `i` or `<Tab>` goes back to the box, `q` cancels. Provider, Model,
Permission mode and Thinking show every option, what is set lit and the
rest dim, so you read the whole choice before you send. Their letter
(`p` `s` `m` `t`) opens the list in your picker (|paseo-pick|), as does the
base branch's `…`, and a click on an option picks it. Start, Where and the
features stay chips you press. The daemon names a new session (and a
worktree's branch), and titles the agent from your message.
Everything you pick is remembered per project and pre-filled next time.
`:Paseo settings mode`, `thinking` and `model` on a draft open its own lists.

A draft is a buffer like an agent's (`paseo://new/new session` on the
bufferline, its choices), and you can have several. Switch to
another agent or terminal and back, and the draft's choices and what you
typed are as you left them; `q` on the choices throws it away. Each draft
is a row on the rail, under the workspace it was opened on, named by the
first line you wrote ("new session" until then); `<CR>` on it goes back.

Drafts are kept across restarts, in `stdpath("state")/paseo/drafts.json`:
the drafts you quit with come back the next time the Paseo tab opens, the
text in the box and the choices above it, with what you opened still in the
middle. A draft leaves the file when it is sent, or thrown away with `q` or
`:bdelete`. Only text is kept: an image attached to a draft is not.
A draft opened and left untouched (nothing typed, nothing picked) is not
kept.

                                                             *paseo-terminals*
                                                         *paseo-terminal-keys*
Terminals ~
A Paseo terminal is a real terminal buffer on the daemon's PTY, listed beside
the agents. It takes every key except these (|paseo-config.ui.terminal|):

    <C-g>       out of terminal mode, without closing anything
    <C-l>       back into the terminal
    <C-j>       the next agent or terminal (`prev` is unbound by default)
    <C-s>       into the rail
    q           (normal mode) back to the agent; the terminal keeps running

                                                            *paseo-subagents*
Subagents ~
`gs` lists the agent's subagents in a live chooser, with a spinner and a
clock on each running one. A Paseo subagent opens as a chat you can message;
a provider's own (Claude's Task tool) opens read-only and follows along. The
rail shows them under their parent too.

                                                            *paseo-permission*
                                                       *paseo-permission-keys*
Permission requests ~
When an agent asks to run something, a dialog opens over the chat:

    1-9         choose that action
    y           the first "allow"
    n           the first "deny"
    N           deny and stop the turn
    <Esc> q     later: the request stays pending; `gp` reopens it

`<Esc>` never denies. A subagent's request is asked in its parent's chat. To
be asked less, change the permission mode (|:Paseo-settings| `mode`).

                                                  *paseo-permission-questions*
                                              *paseo-permission-question-keys*
Questions ~
An agent's multiple-choice questions take over the chat window, one question
at a time (`2 of 3`):

    1-9         pick that option          j k       move
    <Space>     pick the one you are on   <CR> y    send, once complete
    h l         previous / next question  i o       answer in your words
    c           a note on your answer     x         clear this answer
    s           skip (where allowed)      n N       decline (N stops too)
    <Esc> q     later; `gp` reopens it

                                                       *paseo-permission-plan*
                                                  *paseo-permission-plan-keys*
Plans ~
A plan to approve is shown in the same place, as a real buffer you can
scroll and search. Its buttons are the daemon's, the same ones the Paseo
app shows, numbered in that order:

    1           Reject, and keep planning
    2           Implement; the agent moves to accept-edits
    3           Implement with <mode>: back to the mode you were in before
                planning. Offered only when that was Bypass Permissions or Auto
    y           Implement (the same as 2)
    n           reject and keep planning
    N           reject and stop the turn
    j k <C-d> <C-u> gg G    scroll the plan
    <Esc> q     later; `gp` reopens it

6. ASKING ABOUT CODE                                   *paseo-ask* *paseo-ref*

|:Paseo-ask| and |:Paseo-explain| send an agent a REFERENCE: the file's
absolute path and the line range, not the lines themselves, so the agent
reads the file as it is now. (A pure deletion is the exception: its lines are
no longer in the file, so the hunk is quoted.) The reference is taken when
you press the key, not when you send.

                                                  *paseo-ask-chips* *paseo-ask-box*
Chips ~
`:Paseo ask` opens the chat beside your code, in the sidebar, puts the
reference in its composer as a chip, and leaves you in insert mode after it:
>
    @lua/paseo/ref.lua:42-58 why does this skip deletions?
<
The chip is the attachment, the way `[Image #1]` is for an image
(|paseo-images|). It is plain text, so you can move over it, yank it and
undo it, and the agent reads `@path:lines` as a mention. Delete it, or any
character of it, and the reference no longer goes. When you send, what each
chip points at goes ahead of your question.

Chips stack. Go back to the code (`<C-w>p`), ask about another hunk or
selection, and the next chip joins the message you are writing. The same
place twice is one chip. A whole file is `@path`, and `:Paseo ask qf` adds
the whole quickfix list as `@quickfix`, whoever built it: a review workflow
of your own (|paseo-git|), `:grep`, diagnostics.

Which chat: the one in the sidebar, if the file is inside the directory it
works in. Otherwise the agent for the file's repository, brought beside the
code if it was full screen. With no agent there yet, the new-task screen
(|paseo-new|) opens in the sidebar with the chip already in its composer.

`:Paseo explain` adds the chip and the rubric, and sends them at once. On a
new-task screen it waits for you to send.

With |paseo-config.review.agents| the agent is told about the other agents
working in the same tree.

7. WORKSPACES                                               *paseo-workspaces*

The workspaces are Paseo's: one made in the app is as real as one made here.

                                                      *paseo-workspaces-keys*
The workspace chooser ~
|:Paseo-workspaces| lists this project's workspaces (`all`: every
project's), with what each one's agents are doing, updated live.

    <CR> l      open it: `tcd` there (|paseo-config.workspaces.open|) and
                show its chat
    s           its agents (|paseo-agents-keys|)
    n           a new session: the new-task screen, on a new worktree
    d           archive it (asks first if it has unmerged work)
    a           this project's / every project's
    r           review it: `tcd` there and fire `User PaseoReview`
                (|paseo-review-autocmd|)
    q <Esc>     close

                                                          *paseo-agents-keys*
The agent chooser ~
|:Paseo-agents|, or `s` on a workspace:

    <CR> l 1-9  open its chat
    n           a new agent in this session
    y           copy its ID
    d           archive it
    q <Esc>     close

                                                                    *paseo-ws*
                                                      *paseo-workspaces-multi*
Multi-repo workspaces ~
A project that is a directory of several repositories can describe itself in
`.workspaces/workspace.toml`. A new workspace then gets a worktree of EACH
repo, side by side under `.workspaces/<name>/`, on one branch name, and
agents run in that directory and see all of it.

`:Paseo ws init` writes the manifest on a screen: which repos are in, the
base branch of each, and which sibling directories are shared context. >
    <CR>        include this repo / keep this directory
    b           the focused repo's base branch
    t           edit it as TOML instead
    c           write it
    q           cancel; nothing is written
<
After that, "New worktree" on the new-task screen assembles one, and
`:Paseo ws create {name} [repo,repo]` does it by name. A single repository
needs no manifest: Paseo's own worktrees are used.

==============================================================================
8. CHOOSERS                                                     *paseo-choose*

The lists that do more than pick -- the workspace, session, agent and
subagent lists and the rail's `.` menu -- are the plugin's own chooser: a
real buffer in a float, one line per choice, and the cursor is the
selection. Every other choice opens in your picker (|paseo-pick|).

    j k <Down> <Up>     move (counts work)
    gg G                first / last
    / n N               search, as anywhere
    <CR> l              pick
    1-9                 pick that row directly
    q <Esc>             cancel

Anything else a list can do is a plain key, shown in its footer. Leaving the
window cancels it.

`require("paseo.ui.choose").select(items, opts, on_choice)` has the signature
of |vim.ui.select()|, for your own code (|paseo.ui.choose|).

                                                                  *paseo-pick*
Every other "pick one" opens in YOUR picker: whatever has replaced
|vim.ui.select()| (snacks, telescope's ui-select, fzf-lua, mini.pick, ...),
with your keys and your layout. That is the settings lists (a provider, a
model, a permission mode, a thinking level), a base branch, a fork's
destination, "change the model or fork?", and every yes-or-no: archive an
agent, kill a terminal, remove a project, quit with work running. A
yes-or-no lists the safe answer first, so `<CR>` does nothing.

Each call passes a `kind`, for a picker that configures by kind:
`paseo.provider`, `paseo.model`, `paseo.mode`, `paseo.thinking`,
`paseo.branch`, `paseo.fork`, `paseo.model_change`, `paseo.confirm` and
`paseo.quit`. In a settings list, what is set is listed first and marked
`●`; a mode that skips every permission check is marked `⚠`. With no picker
plugin installed, the builtin |vim.ui.select()| is an unsearchable numbered
list, so the chooser above is used instead.

The settings themselves are cards (|paseo-settings|).

                                                                *paseo-search*
Search ~
|:Paseo search| (`<Plug>(paseo-search)`) is the app's Ctrl+K, with one
addition: it also searches what you said. It has no default key (`<C-k>` is
window-up in most configs), so give it a global one: >lua
    vim.keymap.set("n", "<leader>ps", "<cmd>Paseo search<cr>")
<
It shows one list of:

    agent       every live agent, the ones waiting on you first; matched
                on its title, workspace, branch and provider
    ws          every workspace; matched on its title, project and branch
    prompt      every message you have sent in a live chat, newest first,
                from the daemon's prompt index; matched on the message
                and the chat's title
    archived    up to 200 archived chats, most recent first; matched on
                the title, workspace, branch and project

A prompt is matched by what you typed into it. The agent's replies are not
searched. An empty query lists the kinds in the order above, and typing
ranks them all together. With telescope installed (|paseo-requirements|)
the sorter is yours and the preview window shows the chat: the end of it,
or, for a prompt, everything from that message on. `<CR>` opens what you
picked:
  - an agent, in a chat;
  - a workspace, as |:Paseo-workspaces| would;
  - a prompt, in its chat with that message at the top. Older history is
    loaded back to it, up to 600 items.
Without telescope the list opens in the chooser above (|paseo-choose|),
with no preview.

The workspaces and live agents show at once. The prompt lists and archived
chats arrive together a moment later, and are kept for 30 seconds, so the
next search opens with all of them.

require("paseo.git") ~                                             *paseo-git*

The git data layer a review workflow of your own is built on. No UI; it never

                                                                  *paseo.Hunk*
                                                                              
A hunk: >lua
    { repo = <paseo.Repo>, path = "app/main.py", lnum = 42,
      added = 7, removed = 2, kind = "change",  -- add|change|delete|new
      file_deleted = false,
      lines = { "@@ -40,2 +42,7 @@", "-old", "+new" } }
<
`lines` is the hunk verbatim; `stage()` applies it, so keep it intact.

                                                               *paseo.BufHunk*
                                                                              
A buffer hunk: >lua
    { start = 9, count = 0, vend = 9, removed = 3, kind = "delete",
      lines = { "@@ -10,3 +9,0 @@", "-10", "-11", "-12" } }
<
`start`..`vend` is the lines it occupies. A pure deletion occupies the one
line above the removed block (`start = 0` at the top of the file), and its
`lines` are the only copy of the text it removed.

`:checkhealth paseo` reports git; which daemon answered, and
where; the sidecar runtime, and whether the sidecar is running; the
clipboard image readers; the microphone recorder; the installed skills.

The sidecar starts on the first request and stops when Neovim exits.
`require("paseo.bridge").stop()` stops it by hand.

`PASEO_PERF=1 nvim`, or `:lua require("paseo.perf").show()` once, records
where the plugin spends its time; `show()` again prints it, and
`require("paseo.perf").reset()` starts the count over.
